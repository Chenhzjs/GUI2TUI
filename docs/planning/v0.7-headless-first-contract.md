# GUI2TUI v0.7 Headless-first Product and Environment Contract Revision

This document records the user-approved revision to GUI2TUI's product
positioning and candidate 1.0 environment contract. It supersedes the earlier
desktop-first **planning priority**, but it does not alter historical validation
facts in Discovery or phase handoffs. In particular, it does not turn any
`NOT TESTED` row into a pass.

This revision changes documentation and future qualification planning only.
No production or test code changed, and no new environment was installed,
started or qualified while preparing it.

## 1. Why the contract changed

The original v0.7 plan made an ordinary local Linux X11 desktop a core target
and a required 0.7C exit row. That overemphasized traditional desktop
deployment. GUI2TUI is most useful when the user cannot interact with a GUI
directly and has only a terminal, while the application still has the
graphical runtime infrastructure it needs.

The existing implementation and evidence already point in that direction:

- the TUI consumes public AT-SPI semantics rather than pixels;
- the Managed helper creates Xvfb, a private session D-Bus and AT-SPI without
  requiring a full visible desktop environment;
- session selection is explicit and remains separate from application
  authority; and
- installed-binary evidence has qualified this Managed topology on Ubuntu
  24.04 aarch64.

The product contract is therefore now **Headless-first**. Ordinary graphical
desktops remain useful compatibility environments, but they are not a
prerequisite for the core Headless path.

## 2. Product position

GUI2TUI's core goal is:

> In an environment where the user has no directly interactive graphical
> desktop and can interact only through a terminal, make supported semantic
> tasks in otherwise GUI-dependent applications available through that
> terminal.

Primary use cases include a local Linux TTY, an SSH login to a Linux server, a
Linux host with no physical display, a containerized Linux application
environment, a Headless host without VNC/RDP, and a GUI application running in
a background graphical session while the user operates only through a
terminal. A user with an ordinary graphical desktop may also use GUI2TUI, but
that is optional compatibility rather than the defining product premise.

GUI2TUI remains a semantic interaction transformer. It is not a desktop
environment, display server, Wayland compositor, graphical remote desktop,
VNC/RDP client, pixel replica, input-injection automation tool, or collection
of application-specific controllers.

## 3. Graphical runtime is not a visible graphical interface

Headless-first does not mean that an existing GTK, Qt or browser application
can run without any graphical runtime. Such applications may still require an
X11 display server or Wayland compositor. GUI2TUI changes how the user
interacts with the application; it does not remove the application's runtime
dependency.

```text
User
  |
  | Local TTY / SSH PTY / Container TTY
  v
GUI2TUI
  |
  | Public Accessibility semantics
  v
Session D-Bus / AT-SPI
  |
  v
GUI application
  |
  v
Background graphical runtime
  |
  +-- Xvfb
  +-- other qualified headless display server
  +-- qualified headless Wayland compositor
  +-- existing desktop session (optional compatibility)
```

This is the target topology, not a claim that every listed graphical runtime
is implemented or qualified. The core product flow must not require the user
to install GNOME, KDE, XFCE or another complete visible desktop. It may require
the bounded graphical and Accessibility infrastructure declared for the
qualified environment.

## 4. Revised candidate 1.0 environment contract

The categories below are development and qualification directions. A
candidate is not formally Supported until matching real-environment evidence
and the final package/environment qualification exist.

| Environment | Candidate 1.0 classification | Current evidence |
| --- | --- | --- |
| Managed Headless Xvfb | **Core support target** | **QUALIFIED** on Ubuntu 24.04 aarch64 using an installed current-source binary; broader architecture/package qualification remains. |
| Local Linux TTY -> Managed Headless | **Core candidate** | Managed local PTY operation and restoration passed, but a real Linux virtual-console TTY end-to-end run is **NOT TESTED**. |
| Same-host SSH -> Managed Headless | **Core candidate** | **QUALIFIED** on the recorded Ubuntu 24.04 arm64 container topology through a real OpenSSH interactive PTY; client breadth and package integration remain. |
| Docker/OCI Headless | **Important candidate; separately qualified** | **QUALIFIED WITH EXPLICIT LIMITATIONS** on the recorded unprivileged Ubuntu 24.04 arm64 validation topology; no production image or broad OCI matrix is qualified. |
| Ordinary local X11 desktop | **Optional compatibility** | **NOT TESTED** in a real local desktop. Controlled Xvfb is not a substitute. |
| Same-host SSH -> existing desktop | **Optional compatibility** | **NOT TESTED**. It is not a Headless-core exit requirement. |
| Native Wayland application | **Evidence-driven candidate** | **NOT TESTED** in a real native session. |
| XWayland application | **Separate evidence-driven candidate** | **NOT TESTED**; native Wayland evidence cannot qualify it. |
| Headless Wayland compositor | **Headless candidate / feasibility unknown** | **NOT TESTED**; no compositor is bundled or qualified. |
| VNC/RDP or independent remote desktop | **Outside the Headless core; optional future compatibility** | **NOT TESTED**. |
| Cross-host Remote Companion | **Deferred until after 1.0** | Unsupported: no cross-host semantic transport, remote locator or remote authority model exists. |
| macOS/Windows GUI backend | **Outside the Linux AT-SPI 1.0 baseline** | Unsupported as a semantic backend. |

### Managed Headless Xvfb

This remains the concrete 1.0 core target. The 0.7C evidence for Ubuntu 24.04
aarch64 remains valid: user-prefix installation, create/reuse/stop/recreate,
explicit session selection, Doctor, fresh application selection, semantic
operation and authoritative readback, dynamic continuation, external-handler
handoff, terminal restoration, cleanup and uninstall all passed. That result
does not qualify other distributions, architectures, terminal topologies or
display servers by implication.

### Same-host SSH and Local TTY

The core SSH candidate is an interactive SSH PTY into the same Linux host and
user context in which GUI2TUI, the chosen session D-Bus/AT-SPI registry and the
GUI application run. The GUI application may use a background Managed
graphical runtime; no graphical remote desktop is required. Real evidence must
cover terminal input, explicit Managed selection, fresh application selection,
semantic operation/readback, external-editor handoff, normal exit, controlled
disconnect boundaries and owned-process cleanup. Environment variables or a
local PTY do not qualify SSH.

The bounded 0.7C supplement qualified the SSH topology using a real OpenSSH
client/server connection and interactive PTY. It covered current-source
user-prefix installation, Doctor, explicit Managed selection, fresh
application selection, semantic operation/readback, dynamic continuation,
normal terminal restoration, Vim handoff, abrupt transport loss and fresh
reconnection. This is evidence for that exact topology, not every SSH client.

The current Managed architecture is compatible with a local text-only login,
but local-PTY, Docker and SSH evidence are not proof of a Linux virtual
console. A real Local TTY -> Managed run is required before that exact topology
can be labelled Supported.

### Docker/OCI Headless

Containerized Headless deployment is an important candidate because it can
bundle the application's graphical runtime without requiring a host GUI. The
bounded 0.7C supplement proved that a normal non-root container user can run
GUI2TUI, Xvfb, session D-Bus, AT-SPI and controlled GTK applications; use an
interactive `docker exec -it` TTY; coordinate exact startup and cleanup with
the existing Managed lifecycle; and reject the old descriptor and authority
after a container restart before fresh selection.

The qualified validation topology did not depend on the Docker host's GUI,
X11 socket passthrough, graphical-device passthrough, privileged mode or host
PID namespace. It reused the existing Managed session and public AT-SPI
architecture. The committed Dockerfile is a reproducible live-validation
fixture, not a production image, installer or claim covering other engines,
architectures, distributions or applications.

### Ordinary desktops

An ordinary local X11 desktop and SSH attachment to an existing desktop remain
valid compatibility candidates. Their prior `NOT TESTED` status is unchanged.
They may be qualified during a specifically authorized compatibility run,
1.0 integration, or a later release if no 1.0 support claim depends on them.
Their absence no longer blocks closure of the Headless-core portion of 0.7C.

### Wayland families

Native Wayland, XWayland and Headless Wayland are separate rows. An ordinary
Wayland desktop can supply useful native/XWayland semantic evidence, but it
does not prove that a headless compositor works. Lack of trustworthy global
geometry must degrade presentation safely; it must not revoke otherwise valid
semantic interaction. Wayland is not an unconditional v1.0 release gate: each
row may become Supported, Experimental, Not Tested or Deferred according to
real evidence.

### Cross-host boundary

SSH and container use do not imply a Remote Companion. If the TUI process,
AT-SPI backend and GUI application remain within one Linux host/runtime, the
semantic model is still same-host. A local GUI2TUI controlling an application
on another host remains deferred beyond 1.0.

## 5. Revised 0.7C exit contract

0.7C is now **COMPLETE / VALIDATED FOR THE CLAIMED HEADLESS TOPOLOGIES, WITH
EXPLICIT LIMITATIONS**. The original contract-revision commit did not complete
it; the later, separately authorized Headless qualification supplement supplied
the required SSH evidence and the independently authorized Docker candidate
evidence.

Evidence retained without rerun:

- Managed Xvfb on Ubuntu 24.04 aarch64 remains qualified on its recorded
  topology.
- The two controlled Accessibility universes remain valid session-isolation
  evidence, but not ordinary-desktop evidence.
- Managed local-PTY terminal restoration and external-handler results remain
  valid Managed evidence, but not SSH or Linux virtual-console evidence.

New bounded evidence:

- Docker Headless plus interactive `docker exec -it` is qualified on the exact
  unprivileged Ubuntu 24.04 arm64 validation topology.
- Same-host SSH -> Managed Headless is qualified on that topology through a
  real OpenSSH interactive PTY, including external Vim handoff, terminal
  restoration, controlled abrupt disconnect and fresh reconnection.
- Container restart rejects the stopped session descriptor and does not revive
  an old application generation, locator or binding. A newly created Managed
  session requires fresh registry enumeration and explicit selection.
- Linux native virtual-console TTY remains **NOT TESTED**. Therefore the exact
  Local Linux VT topology is not currently claimed Supported.

The revised Headless-core close requires:

1. Preserve the existing Managed qualification and rerun only what a later
   fixed candidate or material environment change requires.
2. Qualify real SSH -> Managed Headless using an installed binary, interactive
   PTY, explicit session and application selection, semantic operation with
   authoritative readback, dynamic continuation, external-handler handoff,
   normal exit and a bounded controlled disconnect/cleanup assessment.
3. Qualify Local Linux TTY -> Managed Headless if that exact topology will be
   labelled Supported; a generic local PTY is insufficient.
4. Preserve Desktop/Managed isolation, fresh application authorization,
   terminal single ownership, private artifacts and bounded cleanup.
5. Keep incomplete rows explicitly Not Tested, Limited or Deferred rather than
   weakening lifecycle, privacy or correctness requirements.

Ordinary local X11 and SSH -> existing desktop are separate compatibility
rows and are no longer Headless-core 0.7C exit gates. They remain `NOT TESTED`
until a separately approved real environment supplies evidence.

The separately authorized Docker/OCI slice has now run. It establishes bounded
runtime feasibility and behavior, not a shipping image or final package
contract. 0.7E must still perform package and integrated qualification if
Docker is retained in the claimed 1.0 matrix.

## 6. Revised 0.7D contract

0.7D remains **PLANNED / NOT AUTHORIZED**. Its Headless-first investigation
order is:

1. Determine whether a maintained Headless Wayland environment can provide
   the session, Accessibility and lifecycle properties GUI2TUI needs.
2. Qualify public AT-SPI semantics and exact operations for native Wayland GUI
   applications.
3. Qualify XWayland applications independently.
4. Prove that absent or inconsistent geometry changes presentation only and
   leaves a usable semantic fallback.
5. Assess session D-Bus, AT-SPI, terminal and external-handler lifecycle in
   each topology.
6. Classify each row from evidence; defer rows whose evidence is insufficient.

No compositor-specific semantic backend, visual inference, input injection or
screen-capture workaround is implied. Ordinary Wayland desktop evidence is
auxiliary and cannot alone qualify Headless Wayland.

## 7. Revised 0.7E contract

0.7E remains **PLANNED / NOT AUTHORIZED**. It retains current-source native
x86_64/aarch64 archive, ABI, layout, installation, privacy and integration
qualification, but organizes the final matrix around the Headless-first
contract.

Every environment ultimately labelled Supported must demonstrate repeatable
installation/uninstallation without requiring a complete desktop environment;
connection to the correct background graphical/Accessibility session; fresh
application discovery and explicit selection; correct semantic operation and
authoritative readback; v0.4-v0.6 dynamic/lifecycle invariants; safe external
handler and artifact behavior; terminal restoration; and a support statement
no broader than the evidence. Evidence from an ordinary desktop cannot qualify
SSH, Docker, Local TTY or another Headless topology by analogy.

If a candidate such as Docker or a Wayland row lacks the required prior
environment evidence, 0.7E must classify it accurately rather than making it a
silent package requirement or pretending it passed.

## 8. Architecture, authority, privacy and safety remain unchanged

This positioning revision does not change the semantic architecture:

- authority remains `RuntimeSessionId` + `ApplicationGenerationId` + exact
  `BackendLocator`, current `InteractionScope`, current capability and
  operation ticket;
- current public Accessibility reads and authoritative readback establish
  truth; events only wake or invalidate;
- full refresh starts from the current public Accessible tree;
- session or transport recovery never reauthorizes an application;
- application selection is explicit and fresh; names, titles, PID, display,
  geometry, indices and historical state never restore authority;
- non-idempotent operations are never replayed automatically;
- PasswordText is never read, exported, logged or handed to an external
  process;
- private artifacts and candidates retain their 0700/0600 ownership and
  lifecycle rules;
- external modality and external work do not extend semantic mutation
  authority, and GUI2TUI never edits an application's backing file; and
- terminal input has one owner, while continuation remains user-directed.

Headless, SSH and container deployment do not justify DOM/CDP, UNO, private
toolkit APIs, OCR, screenshot semantics, GUI input injection, fuzzy matching,
application-specific production branches, a new runtime identity, a general
session/deployment manager or a cross-host protocol.

## 9. Recommended evidence order

Each item requires separate user authorization:

1. If Local Linux VT is intended to be a 1.0 Supported row, run a separately
   authorized real virtual-console TTY -> Managed qualification; otherwise
   retain its accurate `NOT TESTED` status.
2. Authorize 0.7D only when suitable native, XWayland and preferably Headless
   Wayland environments are available; classify rather than force inclusion.
3. Run 0.7E against only the final claimed support rows and architectures,
   including Docker only if it remains in that matrix.
4. Perform the separate v0.7 milestone close; do not infer it from any single
   environment result.

The original positioning revision performed no environment work. The later
[Headless qualification supplement](../validation/v0.7/headless-first-qualification/HANDOFF.md)
records the new Docker and SSH evidence without rewriting that historical fact.
