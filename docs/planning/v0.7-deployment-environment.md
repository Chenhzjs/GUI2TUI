# GUI2TUI v0.7 Deployment & Environment Completeness Discovery

This document records the evidence and planning result for the v0.7
Discovery. It does not authorize implementation, change the package version,
or declare any new environment supported. `AGENTS.md` remains normative.

> **Post-Discovery contract revision:** The evidence and implementation
> findings below remain historical facts. The later
> [Headless-first contract revision](v0.7-headless-first-contract.md)
> supersedes the original environment **priority** and phase-exit proposal:
> Managed Headless is the concrete core target, terminal-only access is the
> product premise, and an ordinary desktop is optional compatibility. No prior
> `NOT TESTED` result was promoted by that documentation change.

## 2. Existing deployment architecture

```text
interactive terminal / PTY
        |
        v
GUI2TUI CLI/TUI process ---------------- configured direct-argv handler
        |                                      |
        | zbus session connection              +-- private candidate artifact
        v
session D-Bus -- org.a11y.Bus.GetAddress
        |
        v
AT-SPI accessibility bus / registry
        |
        +-- application enumeration
        +-- exact application selection
        +-- per-current-view event subscription
        +-- public Accessible tree and capabilities
        +-- exact semantic operations and readback
        |
        v
GUI applications in the same accessible graphical user session
        |
        +-- X11 display or Wayland compositor used by the applications
        +-- toolkit accessibility bridge / direct AT-SPI implementation

optional same-host components:
  headless-session -> Xvfb + private session D-Bus + AT-SPI registry
  gui2tui-local    -> private Unix socket for External Modality resources
```

`AtspiBackend::connect` first opens the session D-Bus with zbus and then opens
the accessibility connection. The `org.a11y.Bus` service supplies the separate
accessibility-bus address. Application discovery enumerates the registry root;
selected objects use exact D-Bus unique names and object paths as
`BackendLocator`s. This is a same-host session-bus architecture. There is no
production client/server semantic transport, Remote Companion, cross-host
authentication, or remote event/cache protocol.

The semantic backend has no Xlib, XCB, compositor, GTK, or Qt dependency. It
uses public AT-SPI over D-Bus. GUI applications still need a functioning
graphical session and their accessibility bridge. GUI2TUI must be able to
reach the same accessibility bus as those applications; in the current
product this normally means the same operating-system instance, user, and
graphical session.

## 3. GUI session, D-Bus and AT-SPI dependency chain

`DBUS_SESSION_BUS_ADDRESS` or the platform's ordinary session-bus discovery
selects the session D-Bus. `org.a11y.Bus.GetAddress` then locates the AT-SPI
bus. `DISPLAY` and `WAYLAND_DISPLAY` are not semantic-backend inputs, but they
are required by the relevant GUI application/display stack and by tools that
launch applications into that session. Native Wayland clients also rely on a
valid `XDG_RUNTIME_DIR` for the compositor socket. `XDG_SESSION_TYPE` is
descriptive and is used by the current X11-only static capture provider; it
does not establish semantic authority.

The persistent headless helper deliberately supplies `DISPLAY`,
`DBUS_SESSION_BUS_ADDRESS`, `XDG_SESSION_TYPE=x11`, `NO_AT_BRIDGE=0`, and
`QT_LINUX_ACCESSIBILITY_ALWAYS_ON=1` before GUI2TUI initializes asynchronous or
D-Bus state. A normal desktop should provide its own session environment and
does not need another Xvfb or private bus.

Different users are not interchangeable. Running as root does not grant safe
access to another user's session, and copying another user's bus/display
credentials is not a supported permission model. Current authority identity
also assumes D-Bus-local unique names and object paths; they cannot be exposed
as cross-host authority without a new authenticated session protocol.

## 4. Current installation and startup paths

The repository currently supports:

1. source build with the pinned Rust 1.88 toolchain and Cargo locked
   dependencies;
2. manual extraction of a Linux release archive, with `gui2tui` in `bin` and
   helper programs in `libexec/gui2tui`;
3. manual copying into a user prefix such as `~/.local`;
4. optional creation of a managed Xvfb session through `gui2tui setup`;
5. direct connection to an already running desktop/session; and
6. saved direct-argv application launchers with a bounded AT-SPI registration
   wait.

There is no package-manager integration, automatic updater, automatic
uninstaller, system daemon, or privileged installer. Rust is needed only for
source builds. Release binaries are dynamically linked to the ordinary GNU
runtime libraries; the v0.3.0 build gated the declared artifacts to glibc
2.35 or older and measured a maximum requirement of glibc 2.34. Current HEAD
has not received a new package/ABI qualification.

Launchers execute an argv vector directly without a shell, validate the
executable, request accessibility enablement through the current public
session service, and wait for a unique new AT-SPI registration. Ambiguous
application matches require explicit selection. An application that was
already running and one launched by GUI2TUI ultimately enter through the same
current registry enumeration and exact selection path.

## 5. Linux X11 evidence and gaps

The strongest evidence is an isolated Ubuntu 24.04 arm64 Xvfb environment
with a session bus, AT-SPI and real GTK/Qt/browser/office applications. It
proves the public semantic backend, interaction authority and lifecycle under
that topology. It does not prove every ordinary local X11 desktop, desktop
environment, login manager, distribution or package layout.

For an existing local X11 desktop, the intended path is to run GUI2TUI as the
same user with that desktop's session D-Bus environment. Starting another
Xvfb/session bus is unnecessary and would create a different application
universe. The current managed-session descriptor is automatically applied
unless disabled; this can make the private session win over a current desktop
and needs an explicit session-selection contract and diagnosis.

Confirmed X11-specific behavior is limited to static visual acquisition:
`HostStaticVisualProvider` requires native X11, one screen, an identity
transform and 96 DPI; it invokes `xdpyinfo`, `xrandr`, `xwininfo`, `xprop` and
`scrot`, and refuses ambiguous geometry. This optional modality path is not
the semantic backend.

The X11 baseline still needs a real local-desktop installation/first-run
qualification, explicit session-choice behavior, dependency guidance, and
x86_64 plus aarch64 current-source package evidence.

## 6. Wayland and XWayland investigation

AT-SPI is a toolkit/accessibility protocol carried over D-Bus, not an X11
protocol. The current semantic backend does not use X11 APIs, so Discovery
found no evidence that native Wayland requires a second semantic backend.
GTK and Qt expose accessibility through AT-SPI independently of their display
backend.

The unresolved issue is evidence, especially geometry. GUI2TUI requests
AT-SPI `Component.GetExtents` in screen coordinates. The spatial layer rejects
missing, non-positive or sentinel extents and can fall back to semantic/flat
presentation; geometry never grants role, identity, scope or operation
authority. Wayland deliberately prevents ordinary clients from knowing global
positions of other clients' surfaces, so toolkit/compositor combinations may
expose missing or inconsistent screen geometry. Native Wayland evidence must
therefore check application discovery, public tree/capabilities, events,
modal scope, exact operations, geometry degradation and continued usability.

Native Wayland and XWayland are separate rows. A successful XWayland
application cannot qualify a native Wayland application, and X11/Xvfb evidence
cannot be relabelled as either. No suitable session was available during this
Discovery; both are **NOT TESTED**.

Static visual acquisition is explicitly unavailable on Wayland. That is an
External Modality limitation and does not by itself invalidate semantic
operation. A headless Wayland compositor would add a new deployment target
without current evidence and is not required for the proposed 1.0 baseline.

Minimum later evidence is one real native Wayland session with representative
GTK and Qt applications, plus a separately identified XWayland application.
If public semantic access succeeds and geometry degrades safely, no backend
change is justified. If public accessibility is blocked, the failure must be
reproduced before any architecture proposal.

## 7. Headless and Xvfb investigation

`scripts/headless-session` is a bounded same-user helper, not a general
desktop-session manager. Persistent mode creates a private state directory,
starts Xvfb on a dynamically allocated display, starts a private session bus,
enables AT-SPI status properties, records a mode-0600 descriptor, and supervises
and cleans its child processes. Temporary mode uses `dbus-run-session`, Xvfb
and a supplied command or login shell, then cleans the session.

The helper depends on Bash, `dbus-daemon`,
`dbus-update-activation-environment`, `gdbus`, Xvfb, `xdpyinfo` and Python 3.
It suggests the relevant Ubuntu packages. Strictly confined Snap applications
may be unable to see the helper's private bus; current launcher validation
refuses that combination rather than weakening confinement.

The mechanism has extensive validation-fixture evidence and can be a
candidate user entry point, but v0.7 must qualify installation, repeated
setup/status/restart/stop, stale descriptor recovery, process cleanup and SSH
use. It must also make connection to an existing session versus creation of a
new session explicit. No general headless-session service or daemon is needed.

## 8. SSH and remote deployment topologies

### A. SSH terminal, GUI on the same remote host

This topology can reuse the current architecture when GUI2TUI runs as the same
user, receives an interactive PTY, and can select the exact graphical
session's D-Bus/AT-SPI environment. SSH does not itself create a GUI session.
Launching a GUI application additionally needs that session's display or
Wayland environment. A managed Xvfb session supplies a separate explicit
alternative.

The current Ubuntu guest proved that an SSH-origin environment could reach a
session and accessibility bus. It did not include a PTY, accessible app,
semantic operation, external handler or disconnect test. Same-host SSH is
therefore **LIMITED / EXPERIMENTAL**, pending an end-to-end qualification.
SIGTSTP/SIGCONT and ordinary terminal cleanup were validated under Linux PTYs
in v0.6; an SSH disconnect is a distinct transport/process-destruction case
and is not covered by that claim.

### B. Local TUI, GUI on a remote host

This topology is not implemented. The current accessibility connection is to
a local user session. There is no authenticated semantic protocol, remote
session identity, authorization, encryption, event/cache synchronization,
disconnect contract, or decision about where external handlers and private
resources run. Exporting a raw session D-Bus is not an acceptable substitute.

### C. Remote desktop or virtual graphical session

VNC, RDP and virtual desktops may create or select distinct graphical user
sessions. GUI2TUI would have to connect inside the exact session containing
the applications. Some products may reuse the ordinary same-host model;
others isolate D-Bus, display or credentials. No product-specific environment
has been qualified, so these topologies remain **NOT TESTED** rather than
globally supported or rejected.

## 9. Remote Companion decision

Three options were reviewed:

| Option | Result and cost |
| --- | --- |
| A. Same-host runtime, including a same-host SSH TUI | Reuses current session/generation/locator model. Needs session selection, diagnostics and PTY qualification, but no semantic protocol. |
| B. Remote Companion for a local TUI and remote GUI | Requires authenticated and encrypted transport, remote identity/authority, versioning, disconnect recovery, event/cache synchronization, resource location, external-handler ownership and secret boundaries. This is a new component and a high validation burden. |
| C. Defer cross-host semantic transport | Keeps the 1.0 baseline bounded to same-host accessibility sessions and states the unsupported topology honestly. |

Discovery recommends **C**, while retaining A as the candidate 1.0 remote-use
contract. The existing same-host and headless topologies are enough to define a
useful 1.0 product; no evidence makes a Remote Companion mandatory. If the
user requires local-TUI/remote-GUI operation for 1.0, that product decision
must happen before implementation because it changes the v0.7 architecture,
security model and schedule. No companion design or implementation is
authorized by this result.

## 10. Installation, binary and system dependency findings

The release workflow knows how to produce native GNU/Linux x86_64 and aarch64
archives and smoke their layout on Ubuntu 22.04. The current binaries use
ordinary glibc/libgcc/libm dynamic dependencies and do not link GTK, Qt or
libatspi directly. Runtime AT-SPI services, D-Bus and a graphical environment
remain system responsibilities.

The gaps for 1.0 are a repeatable current-source archive qualification,
documented supported Ubuntu versions and runtime packages, first-run PATH and
helper discovery, install/uninstall instructions, and clear separation of
desktop versus managed-headless setup. Debian and other Linux distributions
have no attributable live qualification. deb/rpm/AppImage/Flatpak/musl
packages are not present and are not required merely to close v0.7.

## 11. Doctor and failure diagnosis

Current Doctor correctly and privately reports:

- Linux versus build-only non-Linux;
- descriptive session type and presence of display variables;
- TTY plus non-dumb `TERM` at a coarse level;
- configuration validity and saved launcher availability;
- private runtime-directory and bounded artifact ownership health;
- session D-Bus reachability;
- `org.a11y.Bus.GetAddress` reachability;
- AT-SPI connection and accessible-application count; and
- an optional local External Modality endpoint.

It avoids app names, GUI content, bus addresses and resource payloads. A zero
application result is a warning distinct from a missing backend.

It does not yet distinguish display-variable presence from display/compositor
reachability, current desktop from an automatically selected managed session,
wrong user from absent or stale session infrastructure, native Wayland from
XWayland applications, duplicate-name selection, an existing application with
insufficient public Accessibility, or a configured complex-text handler that
is not executable. Terminal diagnosis does not check UTF-8, dimensions,
raw/alternate-screen ability, keyboard enhancement support or SSH PTY
lifecycle. Some session and application deficiencies cannot be inferred from
environment variables alone; bounded public probes and precise recovery
instructions are required.

The minimum improvement is a topology-aware preflight that reports what was
actually probed, distinguishes environment from application semantic quality,
and suggests safe user actions. Doctor must not auto-install services, copy
credentials, change permissions, or reinterpret limited application semantics
as total deployment failure.

## 12. Terminal compatibility and external interaction

The interactive TUI expects a TTY/PTY, non-dumb terminal, UTF-8, usable size,
raw mode and alternate-screen/cursor control. It requests Crossterm enhanced
keyboard reporting and supports ordinary Tab/BackTab, arrows, function keys
and command surfaces in addition to bindings such as Ctrl+Tab and Shift+F6.
Those enhanced combinations vary across terminals and need a compatibility
matrix plus safe existing navigation fallbacks; no second navigation system or
mouse requirement is justified.

v0.6 verified one-reader ownership, resize, external-editor detach/reacquire,
normal exit, SIGINT, SIGTERM, ordinary unwind panic and Linux
SIGTSTP/SIGCONT in a controlled PTY. It did not qualify terminal emulators or
SSH clients. Abrupt connection loss, SIGKILL, power loss and process
destruction still have no userspace cleanup guarantee.

External text handlers remain direct argv with exactly one `{file}` argument,
no shell expansion, a private bounded candidate and final semantic
reauthorization. Environment work cannot weaken those rules. Same-host SSH
qualification must verify that the handler uses the current PTY and that the
TUI resumes with one reader.

## 13. XDG configuration, permissions and private data

Configuration is read from `$XDG_CONFIG_HOME/gui2tui/config.toml` when the
base is absolute, otherwise from `$HOME/.config/gui2tui/config.toml`.
Initialization writes mode 0600 and refuses symlink replacement. Handler and
launcher commands are argv vectors, not shell strings.

Runtime files use `$XDG_RUNTIME_DIR/gui2tui` only when the base is absolute,
owned by the current user and private; otherwise a verified current-UID
temporary fallback is used when the variable is absent. An explicitly unsafe
XDG runtime directory is rejected. Owned namespaces and candidate files remain
0700/0600, leased, capacity bounded and subject to startup recovery/expiry.
Persistent headless descriptors use a private state directory and a 0600 file.

Using sudo or root is not a normal installation or session-access solution.
Deployment guidance must keep persistent configuration, private runtime data
and managed-session state distinct. PasswordText remains excluded from reads,
logs, artifacts and external editing in every environment.

## 14. Candidate 1.0 Environment Support Contract

These are Discovery classifications, not current support promises.

### Candidate Supported after v0.7 qualification

- Linux local X11 desktop, same user and exact graphical/accessibility
  session, on selected Ubuntu LTS versions.
- Linux managed headless Xvfb session using the bundled same-user helper.
- Native GNU/Linux x86_64 and aarch64 archives on the selected Ubuntu/glibc
  baseline.
- Interactive local TTY/PTY with UTF-8, non-dumb `TERM` and the documented
  minimum terminal behavior.

Each row still needs current-source install, session connection, Doctor,
representative operation, lifecycle and cleanup evidence before it becomes
formally Supported.

### Limited / Experimental

- SSH TUI with GUI2TUI and the GUI in the same remote host, user and explicitly
  selected desktop or managed-headless session. The architecture and one
  non-PTY connectivity probe exist; end-to-end PTY evidence does not.
- Optional native-X11 static visual acquisition, limited to its documented
  single-screen/identity-transform/96-DPI conditions.
- Terminals lacking enhanced keyboard reporting when all required tasks remain
  reachable through documented existing fallback keys or command surfaces.

### Not Tested

- Native Wayland semantic operation.
- XWayland application operation.
- VNC, RDP and other independent remote graphical sessions.
- Debian and non-Ubuntu Linux distributions.
- Local desktop environments outside the eventual v0.7 qualification matrix.
- Terminal emulators and SSH clients outside the eventual bounded matrix.

Native Wayland is a candidate for v0.7 qualification, not a presumed
exclusion. Its final status depends on real public-semantic and geometry
fallback evidence.

### Unsupported / Deferred for the 1.0 baseline

- Local GUI2TUI with a GUI on another host; Remote Companion is deferred.
- macOS and Windows GUI semantic backends.
- Different-user or root-mediated attachment to another user's session.
- Wayland static visual capture and a headless Wayland compositor.
- New package ecosystems or a general desktop/session manager unless later
  evidence makes one essential.

## 16. Reusable mechanisms and architecture threshold

v0.7 should reuse the existing AT-SPI backend, runtime/application identity,
exact locators, current-tree full refresh, event ownership, application
selection, terminal guard, direct-argv launchers/handlers, private XDG paths,
headless helper, Doctor and release scripts. Most gaps are session selection,
preflight, packaging documentation and environment qualification.

No `DeploymentManager`, `EnvironmentRegistry`, `DesktopSessionManager`,
`RemoteSessionManager`, process supervisor, plugin framework or second semantic
backend is justified. A new component is admissible only after a reproducible
failure inside the user-approved support contract shows that these mechanisms
cannot express the solution. Cross-host operation clears that threshold in
complexity, but is excluded from the recommended 1.0 baseline rather than
silently implemented.

## 17. Recommended v0.7 implementation phases

Five independently reviewable phases follow from the gaps. All are
**PLANNED / NOT AUTHORIZED**.

1. **0.7A — Environment Contract and Session Selection.** Freeze the approved
   1.0 topology boundary and make existing-desktop versus managed-headless
   selection explicit and diagnosable. No remote transport or session manager.
2. **0.7B — Installation and Diagnostic Completeness.** Close user-prefix
   install/helper/dependency guidance and the minimum Doctor distinctions for
   the chosen contract. No automatic system modification or Doctor rewrite.
3. **0.7C — X11, Headless and Same-host SSH Qualification.** Validate ordinary
   local X11, managed Xvfb and SSH PTY use on the same host/user/session,
   including external handoff and cleanup. No broad application campaign.
4. **0.7D — Wayland and XWayland Qualification.** Use real sessions to decide
   native Wayland and XWayland status, testing semantic access and safe geometry
   degradation. No Wayland-specific backend unless evidence later authorizes a
   separate architecture change.
5. **0.7E — Package and Environment Contract Qualification.** Build/smoke the
   current source for approved architectures, run one integrated deployment
   matrix, finalize public environment wording, and prepare the internal
   milestone evidence. No public release.

0.7A depends on the user's acceptance or revision of the proposed support
contract and Remote Companion deferral. 0.7B depends on that topology. 0.7C
and 0.7D can use the resulting diagnostics and may otherwise be scheduled
independently. 0.7E depends on the preceding supported rows.

## 18. v0.7 milestone exit definition

Milestone Qualification requires all of the following:

1. A user-approved environment contract labels Supported, Limited,
   Experimental, Not Tested and Unsupported/Deferred rows accurately.
2. A new user can install the approved archive or source build in the selected
   Ubuntu baseline and find every required helper without root.
3. Existing-desktop and managed-headless startup select the intended session
   explicitly; GUI2TUI reaches that session's D-Bus, AT-SPI and applications.
4. Failure to connect produces bounded, private and actionable diagnosis that
   distinguishes session infrastructure from application semantic quality.
5. Application enumeration and selection retain current exact authority and
   never infer continuity from name, PID, display, session metadata or
   launcher history.
6. Candidate-supported X11 and headless topologies complete representative
   discovery, operation, event, external handoff and orderly cleanup.
7. The declared same-host SSH status has matching PTY, session, handler,
   suspend/exit and safe-disconnect-boundary evidence.
8. Native Wayland and XWayland are either qualified to their declared level or
   honestly remain outside Supported; geometry loss degrades presentation
   without changing semantic authority.
9. Approved x86_64/aarch64 packages have a repeatable current-source build,
   ABI/layout and fresh-install smoke path.
10. Configuration, runtime data, candidate artifacts and reports retain
    current-user ownership and 0700/0600 privacy; PasswordText remains absent.
11. Existing v0.4-v0.6 semantic authority, full-refresh correctness, event and
    resource bounds, terminal single ownership and external-writeback rules
    remain intact.
12. Unsupported, experimental and untested topologies are never presented as
    Supported; P0 = 0 and P1 = 0 for the approved contract.

These are future exit conditions. Discovery did not run the final v0.7
qualification.

## 19. Explicit non-goals and future boundary

v0.7 does not add GUI interactions, application/toolkit adapters, private
APIs, OCR, screenshots as semantics, input injection, coordinate authority,
fuzzy identity, automatic semantic retry, a general desktop/session manager,
or a new runtime identity. Remote Companion, cross-host GUI control, macOS and
Windows semantic backends, headless Wayland, broad distribution packaging and
new-TTY attachment are outside the proposed 1.0 baseline. v1.0 integration,
RC and release remain separately authorized future work.

## 20. Risks, unverified items and user decisions

- **Required user decision:** accept, narrow or expand the candidate 1.0
  environment contract before authorizing 0.7A.
- **Recommended decision:** defer Remote Companion and cross-host semantic
  operation until after 1.0.
- **Wayland decision remains evidence-bound:** include real native Wayland and
  XWayland qualification in 0.7D, then classify each; do not promise support
  now.
- **Ubuntu version floor:** select exact Ubuntu/glibc targets during 0.7A and
  package qualification; historical v0.3 evidence is informative only.
- **SSH support level:** decide whether successful 0.7C evidence promotes the
  topology from Limited to Supported.
- **Remote desktops and other distributions:** remain Not Tested unless the
  user deliberately adds named rows to the contract.

## 22. Post-Discovery Headless-first revision

The original sections above record the Discovery conclusion that local X11
and Managed Xvfb should both be core targets, that Headless Wayland should be
deferred, and that ordinary local X11 was a required 0.7C row. Those were the
approved planning assumptions at that time and are retained for auditability.

The current user-approved direction is instead:

- GUI2TUI is Headless-first: a local TTY, SSH PTY or container TTY is the
  primary user interface, while a same-host background graphical runtime
  remains available to the GUI application.
- Managed Xvfb is the concrete core target and retains its later Ubuntu 24.04
  aarch64 qualification.
- Local TTY -> Managed and same-host SSH -> Managed are core candidates;
  Docker/OCI Headless is an important separately qualified candidate.
- Ordinary local X11 and SSH -> existing Desktop are optional compatibility
  rows, still NOT TESTED, and no longer Headless-core exit gates.
- Native Wayland, XWayland and Headless Wayland must be classified separately;
  Headless Wayland feasibility is now part of the planned 0.7D investigation,
  not a presumed Supported row.
- Cross-host Remote Companion remains deferred until after 1.0.
