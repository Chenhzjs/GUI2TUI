# GUI2TUI v0.4 Semantic Workflow Reconstruction Discovery

This is a Discovery record, not production authorization. It qualifies the
architectural gap between the publicly released v0.3 verified primitive
interactions and user-controlled continuation across dynamic semantic changes.
It does not implement a workflow engine, a new interaction family, or any
production behavior.

Discovery ran on 2026-09-05 from
`b1a7497be428da0e9bc1b35a7ba463a0a18503d9` on
`v0.4/semantic-workflow-reconstruction`. Source inspection was performed on
macOS. Fresh dynamic evidence was collected in the established OrbStack Ubuntu
24.04 arm64 guest using Xvfb/X11, a session D-Bus, AT-SPI 2.52, the existing
Inspector, existing GTK/Qt fixtures, GTK Demo, and one temporary uncommitted
GTK3 file-chooser fixture. Production source and tests were not changed.

## 1. Current-state architecture inventory

### Runtime session and generation

`RuntimeSession` owns one selected application locator and one
`ApplicationGenerationId`. `open_application` invalidates the prior owner,
cancels its tickets, and creates a new generation. Application disappearance,
explicit application switching, backend loss, and reconnect discard active
editing, content, palette, Choice, modality, and scene state rather than
reconciling a restarted application.

Operation tickets are a bounded map of session ID, application generation,
operation ID, cancellation token, and broad `OperationKind`. They protect
long-running Search, materialization, resource handoff/acquisition, and complex
text interaction from late completion. Ordinary Action, Selection, and Value
dispatch do not use tickets. A ticket contains no target locator, originating
scope, expected semantic condition, observation deadline, or transition result.
It is therefore useful ownership substrate but is not currently a transition
observation contract.

### Node identity and locator

`BackendLocator` is the public AT-SPI bus-name/object-path locator.
`RuntimeNodeId` is the compact cache/scene identity. New application caches
allocate new IDs. Node refresh preserves the ID for an exact locator; subtree
refresh adds IDs for newly realized nodes and removes IDs for disappeared
nodes.

There is an important current inconsistency with the normative contract.
`AGENTS.md` says `RuntimeNodeId` is snapshot-scoped and forbids fuzzy target
reconciliation, but `SemanticCache::reconcile_subtree` also preserves an old ID
across locator change when exactly one old and one new sibling share a
role/name/text-input-kind fingerprint. The cache calls these IDs
"session-stable" and tests this locator churn. This may help presentation and
content position, but it cannot safely transfer operation authority to a
replacement object. Discovery records this as an existing architectural risk;
it does not change the code.

### Event ingestion, invalidation, and refresh

The backend registers public AT-SPI Object, Window, and Cache event families
before bootstrap and buffers them in a bounded queue. Current normalization
recognizes state, property, children, selection, active-descendant, text,
window create/destroy, and cache add/remove. Other signals, including the Qt
Window Activate/Deactivate events observed in this Discovery, become
`Unknown` and conservatively dirty the application.

Events map to node, subtree, or application dirty scopes. Short bursts are
coalesced; children changes refresh a subtree; window/cache/unknown events can
force a full application snapshot. Overflow discards the incomplete prefix and
establishes a fresh full baseline. `ContentRuntime` independently invalidates
affected content and requests a structural rebuild for children/window/cache
changes.

After a generic Action or Selection returns accepted,
`update_from_action_events` waits up to the configured settle deadline for the
first event, gathers a short 40 ms burst, applies refreshes, and otherwise runs
a full refresh. That 40 ms is batching, not semantic proof, and a full refresh
is the no-event correctness fallback. The missing property is that any first
event can currently lead to success wording: no operation-specific semantic
condition is evaluated after the fresh read. The event need not target the
operation and may be an unrelated application change.

Value and text are stronger operation-specific references. Value independently
reads `CurrentValue`; single-line text independently reads complete Text after
submission; complex text compares the complete starting value before write and
reads complete authoritative content afterward. Those paths demonstrate the
desired principle: invocation and events are evidence, but fresh GUI state is
truth.

### Cache, scene, focus, and rebinding

Node and subtree refreshes mutate the canonical cache and rebuild content,
relations, `InteractionScopes`, commands, choices, spatial presentation, and
`TuiScene`. New realized nodes get new `SceneBinding`s from the refreshed
cache. Removed nodes lose their bindings.

Focus restoration first tries `RuntimeNodeId`, then exact `BackendLocator`,
then the first focusable element. Per-scope history stores a scene ID, runtime
ID, and locator so returning from a modal can restore the prior semantic
position. This already supports user continuation when identity is exact. The
fingerprint-based cache reconciliation described above means the first step is
not always exact replacement authority and must be separated from operation
authority before relying on it for transitions.

### InteractionScope and surfaces

`InteractionScopes::analyze` rebuilds Application, Window, Dialog,
ModalDialog, Popup, and MenuPopup boundaries from role, state, ancestry, and
relations. The deepest modal wins; otherwise the deepest popup, focused scope,
or current window wins. Modal/popup scopes filter scene bindings, commands,
Choice, Region Navigator, and invocation so background operations are blocked.

An active dialog is conservatively treated as modal even when the optional
modal state is absent. Popup scopes depend on a public popup-owner relation or
qualified ComboBox structure. This works when the relation/structure exists,
but the fresh Qt menu evidence below exposes no owner relation, so its showing
popup menu remains inside the active Window scope and does not confine the
background.

### Existing multi-step mechanisms

| Mechanism | Retained state and identity | Completion authority | Refresh / disappearance behavior | Who continues? |
| --- | --- | --- | --- | --- |
| Choice overlay | Frozen `SemanticChoice`, selected option index, owner scene ID and owner runtime ID | Public child Action or parent Selection acceptance, followed by refreshed GUI scene; selected state is read from the refreshed cache | Restores exact scene or owner runtime ID; unavailable/replaced strategies refuse | User navigates/selects; GUI2TUI performs one semantic selection |
| Single-line `EditSession` | Runtime ID, exact locator, original text, local buffer, cache generation field, external-change and pending flags | Fresh complete Text read after public `SetTextContents` | Target event marks conflict; locator/capability replacement cancels; scene rebuild preserves exact focus where possible | User edits and commits one write |
| Value adjustment | Current SceneBinding/runtime ID/locator and qualified Value metadata | Independent `CurrentValue` read-back | Exact node refresh or full authoritative fallback; stale/unavailable refuses | User performs each increment/decrement |
| `ExternalTextSession` | Application generation, runtime ID, exact locator, exact scope, original complete text, ticket, private artifact | Compare-before-write plus public EditableText write and complete read-back | App/generation/locator/scope/content change refuses and preserves modified candidate privately | User edits externally; GUI2TUI validates and writes once |
| Modal handling | Rebuilt scope graph and per-scope exact focus anchors | Fresh role/state/tree establish active scope | New modal filters background; disappearance rebuilds prior scope and restores focus anchor | User continues in refreshed modal/prior scene |
| Resource External Modality | Candidate owner/runtime ID/locator, modality ID, ticket, cancellation, negotiated endpoint/artifact lease | Resolver/broker response or explicit snapshot artifact; GUI semantics remain authoritative | Current cache locator and active scope are rechecked; generation/endpoint loss cancels; returning preserves semantic position | User chooses a modality action; it is not semantic mutation |
| Reader/search | Content root/block identity, view position, bounded search state | Fresh bounded public content reads | Source invalidation, block fallback, root disappearance closes Reader | User continues the content task |
| Region Navigator | Presentation region ID and active region derived from current layout | Current rebuilt scene/layout only | Re-derived after refresh and scope filtering; never owns semantic targets | User navigates current presentation |

No existing mechanism automatically plans or executes a multi-operation user
task. That is a strength: all successful examples remain user-controlled.

## 2. Actual missing-layer analysis

The investigated tasks do not share one dominant missing widget. Their blockers
classify as follows:

| Workflow | Atomic capability | Transition awareness | Identity / rebinding | Scope / surface | Task coverage / presentation | Accessibility limitation |
| --- | --- | --- | --- | --- | --- | --- |
| GTK disclosure/tree | Production Expand absent | Explicit Expanded/realization postcondition absent | Trigger locator survives; realized child locators are replaced | Same Window scope | Newly realized child should become navigable after refresh | Ownership of sibling realization is not exposed |
| Qt menu command | OpenMenu and item Action already exist | Showing/open and result conditions are not checked | Locators survive this open/close cycle | Menu owner relation absent; no popup scope | Manual selection is otherwise representable | Popup ownership is missing |
| Qt modal dialog | Trigger/Close Actions already exist | Creation/disappearance conditions are not checked by generic dispatch | New dialog gets new identity; removed surface must stale | Current modal analyzer works | Existing scene/focus continuation is largely sufficient | Qt emits Activate/Deactivate as unknown rather than normalized create/destroy |
| GTK file chooser | Trigger/Cancel/Open Actions exist | Dialog lifecycle fits the same observation shape | Many listing cells are transient | Modal scope works | Location, row selection, directory navigation, and confirmation are incomplete | Location semantics are not reliably named; transient table is noisy |

The dominant cross-family gap is **bounded semantic transition awareness after
accepted generic operations**, followed by exact-authority and popup-scope
limitations. Atomic capability/task coverage is dominant inside the file
chooser and for exposing Expand itself; those do not justify calling every
failure a workflow problem.

## 3. Workflow and event evidence

### 3.1 Expand / Collapse and hierarchical continuation

Application/fixture: GTK Demo 4.14.5, disclosure `Constraints`.

- Before: a Button named `Constraints` was Expandable and Expanded and exposed
  the exact actions `listitem.toggle-expand`, `listitem.collapse`, and
  `listitem.expand`. `Simple Constraints` and `Interactive Constraints`
  appeared as later sibling ListItems under the surrounding list, not as
  descendants of the Button.
- Invocation: Inspector selected the exact named collapse/expand action. No
  action index was guessed.
- Collapse event order: a burst of child deletion and defunct events preceded
  `state-changed(expanded=false)` on the same trigger locator. A fresh tree
  retained that locator and Expandable state, removed Expanded, and omitted the
  realized entries.
- Expand event order: cache-added and children insertions populated new sibling
  rows, followed by `state-changed(expanded=true)`. A fresh tree showed the
  trigger Expanded and the realized entries again.
- Restoration: the trigger `BackendLocator` survived, but the restored
  `Simple Constraints` and `Interactive Constraints` locators differed from
  their pre-collapse locators. Old descendant bindings must therefore become
  stale; new bindings must come from the refreshed scene.
- Relations: both the trigger and realized child exposed only their own
  `LabelledBy` relation. No relation tied the realized sibling rows to the
  disclosure Button.
- Focus/scope: no semantically useful focus transition was required; the task
  remained in the same Window scope.

Task-level conclusion: after a fresh scene contains the new sibling rows, the
user could navigate and activate a newly created binding. GUI2TUI does not need
to prove that every row belongs exclusively to this disclosure for manual
continuation. It would need that stronger ownership claim to automatically
find or operate a descendant, so it must not automate that step.

Expand/Collapse classification: **C — invocation is qualified but continuation
ownership remains ambiguous**. Existing refresh is sufficient to expose the
changed scene to the user; an explicit Expanded condition would verify the
state transition, but production invocation remains a missing atomic
capability and was not added.

### 3.2 Menu / popover lifecycle

Application/fixture: existing Qt6 fixture, Tools → Activate Demo.

- Before: `MenuItem "Tools"` was visible and exposed `ShowMenu`. Its child
  popup Menu and `MenuItem "Activate Demo"` already existed but were not
  Showing/Visible; the item exposed `Press`.
- Open: exact named `ShowMenu` returned accepted. About 20 ms later a fresh read
  showed Tools Focused, the Menu Active/Showing/Visible, and the item
  Showing/Visible. Events were trigger `focused=true`, then menu
  `showing=true`.
- Structure and identity: the popup remained the existing child subtree with
  the same locators; it was state realization rather than object creation.
- Scope/owner: Tools and Activate Demo exposed no relations. The current scope
  analyzer retained only the main Window as active; it did not create a
  MenuPopup scope.
- Choose/result: exact named `Press` changed the authoritative label from
  `Status: idle` to `Status: menu activated`. A property-change event reported
  the label name. The menu initially remained showing; it later emitted
  `showing=false` when the modal dialog opened.
- Focus: focus moved to the menu trigger on open, not to the item in the
  captured tree.

Conclusion: the current TUI can already model `OpenMenu`, refresh, expose a
newly Showing menu item, let the user invoke it, and refresh again without a
workflow engine. What is missing is an explicit `menu Showing` open condition,
an item-result/temporary-surface condition where one is known, and safe popup
scope classification. When public ownership is absent, GUI2TUI must not invent
it; either same-window manual continuation must remain conservatively bounded
or the popup must be reported as unconfined/ambiguous.

This does not alter Choice. When complete options already exist, the terminal
Choice overlay remains the better task reconstruction and makes zero GUI
disclosure calls.

### 3.3 Dialog / modal transition

Application/fixture: existing Qt6 modal dialog fixture.

- Creation: exact `Press` on `Open modal dialog` produced a new Dialog locator
  with Active/Showing/Visible state and a focused Close button. Fresh semantic
  detection occurred about 220 ms after invocation.
- Events: Qt emitted descendant Showing changes, Window Activate as an
  `Unknown` event, dialog `active=true`, trigger focus loss, and Close focus.
  It did not emit normalized WindowCreated in this run.
- Scope transition: fresh analysis placed the dialog beneath the existing
  Window as the active `ModalDialog`, so the Window was no longer active and
  background operations were confined by current architecture.
- Completion: exact `Press` on Close emitted Window Deactivate as `Unknown`,
  `active=false`, then Showing false for the dialog descendants and root.
  An immediate fresh tree could still contain the stale dialog object while a
  subsequent scope read had already restored the Window. This demonstrates
  why "one refresh happened" is not itself the completion condition.
- Restoration: after the dialog was no longer semantically Showing, the main
  Window scope was active. Source inspection shows per-scope exact focus
  history is used to restore the prior surface.

Conclusion: current `InteractionScope`, scene rebuild, and focus history
already solve modal authority and ordinary user continuation. The missing
piece is bounded confirmation that a modal scope became active or disappeared,
not a new dialog subsystem or persistent Task object.

### 3.4 File chooser boundary evidence

Status: **INSPECTED, LIFECYCLE ONLY; END-TO-END FILE CHOICE NOT QUALIFIED**.

Application/fixture: temporary uncommitted GTK3 host and a synthetic
`/tmp/gui2tui-v04-files` tree containing two empty files and one nested
directory. No personal file was opened and no file was saved.

- Surface: exact Click on `Open synthetic chooser` created an Active, Modal,
  Showing GTK file-chooser Dialog. The active scope moved from the host Window
  to a `ModalDialog` containing an inner Dialog.
- Events: creation produced a large construction burst. The decisive sequence
  included dialog `showing=true`, application-root child insert, WindowCreated,
  and `visible=true`. Cancel produced many `showing=false` events, root child
  delete, Window Deactivate, WindowDestroyed, and `visible=false`.
- Burst behavior: 1,565 normalized deliveries were observed: 430 state, 453
  property, 125 children, 132 cache-add, 62 cache-remove, 359 unknown, and one
  each of window-create, window-destroy, selection, and active-descendant.
  This diagnostic detail is not a product model; it shows why events must be
  coalesced wakeups.
- Timing: fresh open state was available about 310 ms after invocation; the
  semantic absence condition after Cancel was observed about 30 ms after the
  close invocation. These are measurements, not delays or completion rules.
- Location model: the requested synthetic directory was reflected by the file
  table contents, but the accessible tree did not provide one reliable,
  semantically named current-path field. Two invisible editable Text nodes
  lacked useful names.
- Listing/selection: `Table "Files"` exposed Table and Selection with
  ManagesDescendants. File/directory rows were transient table cells. The first
  row was Selected. File and directory name cells all advertised the same
  `Expand or contract`, `Edit`, and `Activate` actions, which is insufficient
  by itself to infer directory navigation versus file choice.
- Confirmation: Cancel and Open were named Buttons with exact Click actions.
  Cancel was exercised; Open was not, because selection and file/directory
  task semantics were not qualified.
- Dynamic directory transition: not invoked. Doing so without first
  qualifying row identity, selection, and navigation semantics would conflate
  missing primitive/task coverage with transition observation.

Boundary conclusion: file-chooser creation, modal scope, and disappearance are
v0.4 transition concerns. Location/path semantics, table-row identity,
selection, directory navigation, Open/Save semantics, and overwrite handling
are substantial v0.5 task/interaction coverage. A full file chooser must not be
forced into v0.4 merely because its surface is dynamic.

## 4. Events versus authoritative reads

Reliable wakeup families in the observed corpus were state-changed,
children-changed, property-change, cache add/remove, and GTK window
create/destroy. Selection and active-descendant remain relevant for collection
tasks. Toolkit variance was real: Qt represented dialog activation through
Window Activate/Deactivate signals currently normalized as Unknown, while GTK
emitted explicit WindowCreated/WindowDestroyed.

Event order is not a portable completion contract. Expand deletion preceded
Expanded false; expansion inserted nodes before Expanded true. GTK file chooser
generated hundreds of construction/destruction events. Qt dialog closure
allowed a transient stale tree even while later scope analysis had restored the
window. A first event can also be unrelated to the invoked operation.

The recommended model is:

```text
accepted public operation
  -> events wake and coalesce observation
  -> fresh semantic read / refreshed scene establishes truth
  -> explicit bounded semantic condition classifies the outcome
  -> user continues in the authoritative scene
```

A deadline only bounds observation. It never proves success. At deadline, one
fresh authoritative observation may classify confirmed, valid alternate,
unchanged, stale, scope-changed, ambiguous, disappeared, or timed out. No fixed
sleep or repeated "probably done" polling is a product completion rule.

Exact causal attribution is unnecessary for the observed tasks. AT-SPI events
carry no operation correlation token, and requiring one would reject useful
public semantics. It is sufficient that the operation was valid at invocation
and that fresh authoritative state within the bound satisfies an explicit
condition. Events remain hints/wakeups, not proof that this exact operation
caused this exact signal.

## 5. Identity, rebinding, and scope findings

What survives:

- application generation survives ordinary subtree/surface changes;
- an exact BackendLocator can survive state-only transition, as in the Qt menu
  and GTK disclosure trigger;
- current cache code preserves the RuntimeNodeId for an exact locator;
- a refreshed scene naturally creates bindings for newly realized targets;
- per-scope focus history can restore an exact prior target after a modal.

What becomes stale:

- realized GTK disclosure descendants received new locators after collapse and
  re-expand;
- dialog/file-chooser nodes disappear on completion;
- subtree replacement can remove bindings even within one application
  generation;
- application restart invalidates the whole generation and every ticket.

Explicit target re-resolution is required only when a future semantic
operation intends to act after the transition. Manual continuation does not
need to carry a target: the user chooses a current SceneBinding. If an
operation does carry a target, it must resolve through the refreshed cache by
exact current semantics and scope. Name similarity, geometry, child index,
nearest node, or the current unique fingerprint heuristic must not grant
operation authority.

Modal scope reuse is strong. Popup scope is conditional: the Qt menu proves
that parentage plus Showing state does not necessarily supply a public owner
relation. Surface disappearance should invalidate its focus/bindings, rebuild
scope, and return to the prior exact focus anchor where possible. A new
unrelated modal is a valid alternate transition that supersedes the expected
surface; it must never be ignored to finish the original action.

## 6. Failure, ambiguity, and negative evidence

At least three negative findings constrain future implementation:

1. GTK disclosure ownership is unproven. Realized rows are siblings and expose
   no relation to the trigger. GUI2TUI may refresh and let the user continue,
   but must not automatically claim or select "the disclosure's child."
2. Qt menu popup ownership is absent. The popup is Active/Showing, yet current
   `InteractionScope` does not classify it as MenuPopup. GUI2TUI must not infer
   owner/scope from title, geometry, or nearby tree position.
3. Current cache fingerprint reconciliation can preserve an ID across locator
   replacement. This is unsafe as mutation authority even when the role and
   name are unique. A replacement must require new authority or exact public
   identity, not implicit continuity.

The outcome model must also represent operation rejected, no semantic change,
unexpected valid transition, target disappeared, application/generation loss,
new modal scope, ambiguous realization, deadline expiry, unusable new surface,
and user cancellation. Correct return to the refreshed scene or refusal is
preferable to retries that guess.

## 7. Existing mechanisms that already solve workflows

No new workflow architecture is needed for:

- complete Choice options: the terminal overlay directly reconstructs the
  choice and deliberately avoids GUI popup lifecycle;
- modal dialog authority after refresh: current scope analysis filters the
  background and current focus history restores the prior surface;
- user navigation to a newly realized node after a scene rebuild: new bindings
  and existing focus/Region Navigator behavior are sufficient;
- single-line text, Value, and complex-text write completion: each already has
  operation-specific authoritative read-back;
- cancellation/return from Reader, Choice, edit, resource modality, and
  external text: their local task state machines already own this lifecycle;
- application-generation loss and long-operation cancellation: current runtime
  tickets prevent late results from entering a new application generation.

The project must not create a second interaction state machine around these
paths.

## 8. Common-pattern analysis

Expand realization, menu state realization, modal dialog scope, and file
chooser surface lifecycle share these useful semantics:

1. a verified public operation boundary;
2. current session, generation, exact origin, and active-scope authority;
3. a bounded, explicit, generically observable semantic expectation;
4. events as wakeups for a fresh read/refresh;
5. authoritative post-state and rebuilt scopes/bindings;
6. outcome classification including alternate transition, unchanged,
   disappearance, ambiguity, cancellation, and timeout;
7. return to the normal refreshed scene for the user to continue.

The three-family threshold is met for a **shared bounded transition-observation
contract**. It is not met for automatic multi-step orchestration: none of the
evidence requires GUI2TUI to remember or execute the next user choice, and the
disclosure evidence specifically prohibits automatic descendant attribution.

## 9. Architecture decision

**B. NARROWER CONTINUATION MODEL SUFFICIENT**

Existing event refresh, cache/scene rebuild, modal scope, exact focus history,
and ordinary user navigation already handle much of dynamic task continuation.
The smallest justified addition is an operation-adjacent, bounded semantic
transition observation contract for dynamic actions, plus a strict separation
between presentation continuity and operation authority across replacement.

The product needs behavior equivalent to:

- capture current session/generation, exact origin locator, and scope;
- invoke one explicitly compatible public semantic operation;
- declare a small operation-specific semantic expectation, such as Expanded
  state, a Showing temporary surface, active modal scope, or disappearance of
  the originating temporary surface;
- use relevant events only to wake/coalesce refresh;
- evaluate the expectation against fresh authoritative semantics until it is
  satisfied, an explicit alternate/failure occurs, or the deadline bounds the
  attempt;
- rebuild scopes, scene, commands, choices, content, and presentation through
  existing machinery;
- return control to the user in the new scene.

The product does not need to prove event causality, retain a persistent Task for
these examples, or automatically execute the next operation. The exact Rust
type shape is deliberately not specified by Discovery.

Do **not** build `Workflow`, `WorkflowStep`, `WorkflowEngine`, `WorkflowGraph`,
a workflow DSL, transition engine, transaction engine, compound semantic
operation, automation planner, event-correlation registry, or application
recipe system. Do not merge resource External Modality and complex-text
interaction. Do not use sleeps, keyboard/mouse injection, coordinates,
anonymous action order, or fuzzy identity.

## 10. Explicit non-goals and milestone boundary

Discovery made no product capability, key, layout, Choice, dialog, Selection,
Expand/Collapse, menu, or file-chooser change. v0.4 is not a widget milestone.

| Family | v0.4 boundary | v0.5 boundary |
| --- | --- | --- |
| Selection | None beyond observing an already supported selection change | deselect, clear, multi-select, select-all, table/list selection coverage |
| Expand | transition contract and honest realization/ownership qualification; any product trigger requires separate evidence/authorization | broad disclosure/tree interaction coverage if the atomic capability remains the blocker |
| Menus | observe open/close/result surfaces and preserve/refuse scope safely; manual user continuation | breadth of menu/submenu/context-menu task coverage |
| Dialogs | reuse current modal scope and verify enter/exit continuation | missing form fields/actions and task-specific completion coverage |
| Tree | refresh and allow manual navigation of current realized descendants; no automatic child search | selection/navigation breadth and unsupported primitive families |
| File chooser | surface creation/disappearance and modal-scope transition only | location/path, directory traversal, selection, Open/Save/overwrite task completion |

v0.6 remains responsible for prolonged multi-application/window churn,
restart/reconnect robustness, overflow longevity, and multi-surface continuity.
v0.7 remains deployment/environment completeness. No v0.8/v0.9 is implied.

## 11. Recommended bounded v0.4 phases

These phases are recommendations only. None is automatically authorized.

### 0.4A — Exact Authority and Bounded Transition Observation

- Question: can one accepted dynamic semantic operation reach a truthful,
  bounded post-state without treating an event or delay as success?
- Authorized scope if later approved: define the minimal observation behavior,
  operation-specific semantic conditions, outcomes, deadline/cancellation, and
  exact generation/locator/scope authority; ensure replacement continuity
  cannot grant operation authority through the cache fingerprint heuristic.
- Explicit exclusions: no new interaction family, user key, workflow/task
  engine, automatic next step, selection, or layout work.
- Live evidence: repeat state-only menu, realization disclosure, and modal
  surface transitions; include no-event, unrelated-event, stale-target, and
  deadline cases.
- Exit: generic action success is based on fresh semantic conditions, not the
  first event; stale/ambiguous replacement refuses deterministically; existing
  Text/Value/Choice behavior is not regressed.

### 0.4B — Dynamic Surface and Scope Continuation

- Question: can the user enter and leave temporary semantic surfaces while
  current `InteractionScope` remains authoritative?
- Authorized scope if later approved: integrate bounded observation with
  already-supported named OpenMenu/dialog actions, rebuild the scene, enter a
  qualified modal/popup scope, and restore prior exact focus on disappearance.
- Explicit exclusions: no menu/widget compatibility campaign, submenu planner,
  Choice redesign, new dialog subsystem, or app/toolkit owner rule.
- Live evidence: Qt state-realized menu, Qt modal dialog, GTK created/destroyed
  dialog/file-chooser surface, and at least one missing-owner refusal.
- Exit: user can continue manually on a qualified new surface and return; an
  ownerless or unusable popup is explained/refused without exposing background
  authority as if it were safe.

### 0.4C — Realization and Hierarchical Continuation

- Question: can a structural transition expose a refreshed hierarchy that the
  user can navigate without claiming unproven realization ownership?
- Authorized scope if later approved: qualify state/realization conditions,
  stale old descendants, new SceneBindings, manual navigation, and honest
  ambiguity. A production Expand trigger is not implied and requires explicit
  approval of its atomic capability.
- Explicit exclusions: no automatic `find child X`, ownership guessing,
  Selection work, fuzzy rebinding, tree recipe, or complete-subtree claim for
  partial/virtualized content.
- Live evidence: GTK sibling realization and one independent implementation if
  readily available; include locator replacement and an ambiguous realization.
- Exit: current realized descendants are reachable after refresh, old bindings
  cannot mutate replacements, and absent ownership blocks automation but not
  honest manual continuation.

### 0.4D — Continuation UX and Theme Qualification

- Question: does the terminal tell the user enough to continue, cancel, or
  understand an ambiguous/failed transition without a workflow status system?
- Authorized scope if later approved: concise states for observing, entered
  surface, no usable surface, cancelled, stale, ambiguous, and timed out;
  representative cross-toolkit task validation.
- Explicit exclusions: no layout redesign, dashboard, automation history,
  broad task-completeness matrix, release/RC work, or v0.5 implementation.
- Live evidence: user-controlled menu, modal, and hierarchical continuations,
  including one alternate transition and one safe refusal.
- Exit: at least three generic dynamic task families return the user to a
  truthful refreshed scene with clear success/refusal and no hidden automatic
  continuation.

## 12. v0.4 exit definition

The v0.4 architectural theme is complete when representative state,
realization, surface/scope, replacement, and completion transitions are bounded
by explicit semantic conditions; events only wake fresh reads; generation,
exact target, and active scope remain authoritative; stale or ambiguous
replacement cannot inherit operation authority; existing scene/scope/focus
machinery enables the user to continue across at least three independent
workflow families; and failures return to an honest usable scene. Completion
is not measured by widget count, automated step count, or application count.

RC should be considered only after that evidence shows the theme complete. No
release phase is reserved by this Discovery.

## 13. Roadmap impact

- `roadmap-to-1.0.md`: only a minimal status/direction refinement is needed;
  the architectural progression remains valid, but v0.4 should be understood
  as bounded transition observation and user continuation, not workflow
  orchestration.
- v0.5: boundary remains and should emphasize primitive/task completeness,
  particularly Selection and file-chooser/table/list coverage.
- v0.6: unchanged; long-running restart, reconnect, and multi-surface
  robustness remain future work.
- v0.7: unchanged.

## 14. Genericity and forbidden-path audit

No application/toolkit-specific production design, input injection,
coordinate action, proportional GUI-to-terminal mapping, anonymous action
guessing, or backing-file mutation was introduced. Validation used application
