# GUI2TUI v0.3 Roadmap

This is the persistent, reviewed roadmap for capability recovery. It is
directional: a later phase is not authorized merely because it is listed.

## Status

- **Discovery — COMPLETED**
- **Phase 0.3A — COMPLETED** (Capability Evidence & Operation Contract Qualification)
- **Phase 0.3B — RECOMMENDED / AWAITING USER AUTHORIZATION** (Native Bounded Capability Recovery)
- **Phase 0.3C — PLANNED / NOT AUTHORIZED FOR IMPLEMENTATION** (Configurable Complex Text Interaction)
- **Phase 0.3D — PLANNED / NOT AUTHORIZED FOR IMPLEMENTATION** (Compound Interaction & Capability UX Qualification)

No v0.3 release phase is defined yet; release qualification follows evidence
from 0.3D.

## Reviewed route

### 0.3A — Capability Evidence & Operation Contract Qualification

Question: **What can GUI2TUI safely invoke and authoritatively verify?**

This phase records public AT-SPI evidence, operation preconditions, safe
probes, invocation versus authoritative outcomes, normalization, stale and
quarantine behavior. It does not expose new user capabilities.

### 0.3B — Native Bounded Capability Recovery

Question: **Which already-qualified small, structured capabilities should
become native TUI interaction?**

Phase 0.3A supplied a controlled Qt6 Slider contract (bounded setter,
authoritative read-back, and restoration). The current recommendation is to
start narrowly with Value controls, then consider a bounded Selection
extension only if its evidence remains generic and stable. Scope must be
re-authorized before implementation.

### 0.3C — Configurable Complex Text Interaction

Question: **How should large/free-form non-secret textual interaction use a
low-coupling user-configurable interaction modality while preserving GUI
authority and verified write-back?**

This is not an `$EDITOR` integration. Any future handler is optional,
application-independent, and receives only a GUI2TUI-owned bounded
representation; it never edits an application's backing file directly.

### 0.3D — Compound Interaction & Capability UX Qualification

Question: **Which genuinely generic multi-step semantic operations are
justified, and how should recovered/unavailable capabilities be presented
clearly?**

Compound behavior must use public semantic operations and bounded
read-back/realization checks; keyboard or mouse injection is never a fallback.

## Long-term principles

v0.3 is not “make all Unsupported controls interactive.” A capability passes
the gate only when it is:

```text
Interface exposed → semantically usable → safe to invoke
→ authoritatively verifiable → user capability
```

Unsupported is preferable to invented capability. The original GUI remains
authoritative and optimistic local state is never semantic truth.

Potential outcomes remain:

1. **Native TUI** for small, bounded, structured operations with explicit
   public capability and reliable read-back.
2. **Configurable external interaction modality** for large/free-form,
   non-secret content where a mature local tool is useful, while GUI2TUI
   retains identity, conflict checks, public write-back, and verification.
3. **Safe degradation** where capability is absent, ambiguous, rejected,
   unsafe, secret, partial without a safe target, or unverifiable.

Single-line versus multiline is not a rule. Payload size, completeness,
range/replace semantics, editing complexity, verification and conflict safety
determine native versus external placement. Existing resource External
Modality infrastructure may supply private artifacts, lifecycle and process
policy, but resource viewing/materialization and semantic state mutation stay
separate abstractions.

The exact next phase is **0.3B — Native Bounded Capability Recovery** and it
is awaiting explicit user authorization. No later phase is automatically
authorized.
