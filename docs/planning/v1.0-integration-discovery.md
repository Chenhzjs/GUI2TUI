# GUI2TUI v1.0 Integration & Stabilization Discovery

## 1. Status and scope

This document records the authorized v1.0 Integration & Stabilization
Discovery. It is a product-readiness review and implementation plan, not an
authorization to implement v1.0, create an RC, change the package version,
move a tag, or publish a release.

Discovery baseline:

- Starting HEAD: `298076239326666dc3abc2eb9c53af216c8c6591`
- Branch: `v0.7/deployment-environment-completeness`
- Package version: `0.3.0`
- Worktree and remote at start: clean and synchronized
- v0.4-v0.7: complete, internally milestone-qualified, with recorded limits
- v1.0 Integration: not started before this Discovery
- v1.0.0 RC/tag/release: not started

The review used the current source, current unit/CLI tests, the v0.4-v0.7
planning and qualification records, installed-package evidence from v0.7E,
the user-facing deployment documentation, and a bounded product CLI probe on
the available macOS development host. No private document, password, user
application, or external service was used.

## 2. Executive conclusion

GUI2TUI is architecturally capable of being a useful 1.0 product for a
narrow, honest Headless-first contract. It is not yet ready to call itself a
reliable 1.0 product.

The missing work is integration and qualification, not a new semantic
framework. The current pipeline already connects public AT-SPI semantics,
spatial presentation, verified operations, dynamic continuation, runtime
authority, modality boundaries, terminal ownership, and managed deployment.
The remaining risk is that the evidence is still distributed across milestone
fixtures and phase handoffs. A user needs one final-source, installed-binary
path from installation to a representative task, dynamic change, recovery,
and safe exit. That complete path has not yet been requalified as one 1.0
contract.

The most important findings are:

1. The v0.5 common-task baseline is qualified historically, but the final
   installed v0.7E package evidence intentionally covered only a representative
   subset. Open File, Choose Folder, PageTab, hierarchy, Reader/partial
   content, and the full task composition must be rerun together before they
   can be release evidence for 1.0.
2. The Headless-first deployment path is real and usable on the recorded
   aarch64 Managed Xvfb, Docker interactive-PTY, same-host SSH -> Managed,
   and Weston Native Wayland/XWayland topologies. The evidence must not be
   generalized to Linux VT, native x86_64 hardware, other distributions,
   other compositors, ordinary desktops, or Wayland over SSH.
3. The TUI has a coherent selector, help, palette, status, scope, partial
   content, and failure model in source and historical live evidence. Final
   integration still needs real terminal observation at narrow/wide sizes and
   through the cross-module scenarios most likely to expose a discoverability
   or recovery break.
4. v0.6 established bounded ownership and resource invariants, but 1.0 still
   needs measurable startup, operation, refresh, and bounded-soak gates on the
   final package. Existing multi-second incomplete-cache startup is a known
   performance boundary, not permission to present an incomplete tree as
   complete.
5. No new P0/P1 product defect was reproduced in this Discovery. There are
   P1-level release gates caused by missing final integrated evidence and
   unresolved support-contract choices; those are evidence/contract blockers,
   not claims of a current semantic safety failure.

## 3. Product architecture and authority

The current product path is:

```text
AT-SPI transport
  -> semantic cache / relational graph / content models
  -> spatial evidence and SpatialTopology
  -> RegionPresentation / responsive TuiLayoutPlan
  -> TuiScene / SceneBinding / current InteractionScope
  -> user-selected UiIntent / SemanticOperation
  -> exact backend operation and operation ticket
  -> authoritative GUI readback
  -> fresh cache, scope, scene, and binding
```

The layers remain correctly separated:

- `src/backend/` obtains public AT-SPI semantics and performs advertised
  operations.
- `src/semantic/` owns snapshot-scoped `RuntimeNodeId`, exact
  `BackendLocator`, roles, relations, state, and capabilities.
- `src/transcompile/` turns semantic structure and trusted geometry into
  presentation; geometry does not grant capability or identity.
- `src/content/` provides bounded Reader, search, table, and virtual
  collection models; `PartialRealized` remains partial.
- `src/runtime/` owns `RuntimeSession`, `ApplicationGenerationId`, tickets,
  cancellation, signals, and resource ownership.
- `src/tui/` owns one scene/focus authority, terminal navigation, overlays,
  help, palette, external handoff, and user-facing status.
- `src/product/` owns explicit session selection, launchers, Doctor, paths,
  installation helpers, and Managed Headless lifecycle.

Operation authority remains the intersection of runtime session, application
generation, exact locator, current scope, current advertised capability,
valid operation ticket, and fresh public semantics. Events wake or invalidate;
they do not prove success. The user continues manually from the fresh scene.
No `WorkflowEngine`, `TaskSession`, application adapter, remote companion, or
second focus/semantic authority is justified by the evidence.

## 8. Headless-first boundary

The strongest evidence-backed 1.0 core is:

- user-prefix installation on GNU/Linux;
- GUI2TUI-managed Xvfb with private session D-Bus/AT-SPI;
- same-host operation through the recorded interactive SSH PTY;
- the recorded unprivileged Docker interactive PTY topology; and
- the recorded Weston headless Native GTK4/Qt6 and XWayland GTK4 rows, each
  with its explicit limitations.

The following remain outside a default Supported claim unless new evidence is
authorized: real Linux virtual-console TTY, native x86_64 full environment
integration, ordinary local X11, ordinary full-desktop Wayland, SSH to an
existing desktop, Wayland over SSH, other distributions/compositors/clients,
Qt over XWayland, VNC/RDP, and cross-host Remote Companion.

Managed setup still requires the application's graphical runtime dependencies
and system packages such as Xvfb, D-Bus and AT-SPI. GUI2TUI does not install
them automatically and does not require GNOME/KDE/XFCE, a physical monitor,
VNC, or RDP for the qualified Managed path. This is an honest deployment
boundary, not a missing semantic backend.

## 9. Performance and long-term stability

Existing evidence is sufficient to preserve the design constraints:

- current-generation queues, event producers, caches, focus history, tickets,
  children, candidates and modality artifacts are bounded or ownership-scoped;
- full refresh is a correctness boundary after incomplete event history;
- large complete Cache bootstrap is fast in the recorded Chrome baseline;
- incomplete Cache bootstrap may take several seconds because correctness
  requires a walk; and
- operation deadlines, cancellation, handler ownership and terminal recovery
  are explicit.

It is not sufficient to close 1.0 because the final package has no single
stability/performance qualification with thresholds. The implementation phase
should measure, at minimum, first usable selector/scene time, complete versus
incomplete 5k-node bootstrap, p50/p95 bounded operation/readback time, event
overflow resync time, terminal redraw after resize, and one bounded multi-step
soak. Measurements must be tied to source, package, architecture, topology,
terminal size and fixture; they must not become universal claims from one
application.

## 10. Architecture conclusion

No new architecture layer is required by current evidence.

The existing authority model, current-scene/manual-continuation model,
content separation, spatial presentation policy, terminal ownership, external
artifact boundary, Doctor/session selection, and Managed helper are the right
abstractions. A new workflow engine, task planner, deployment manager,
Remote Companion, application adapter, semantic backend, or second focus
authority would enlarge risk without solving the demonstrated gap.

If integration discovers a failure, the default remedy is a small generic fix
in the existing layer plus a focused regression and live task evidence. A new
abstraction should require a separate evidence-backed decision.

## 11. Discovery result

**GUI2TUI v1.0 Integration Discovery: COMPLETE.**

The product is a credible internal v0.7 baseline, not yet a 1.0 product. The
next authorized decision should be a bounded integration phase beginning with
G1/G2: final-package common-task qualification and explicit support-contract
freeze. After those gates, usability, stability, and release qualification can
proceed without widening the semantic scope.
