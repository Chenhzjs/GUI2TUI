# GUI2TUI v0.6 Runtime Continuity Roadmap

## 1. Status and authority

The [v0.6 Discovery](v0.6-runtime-continuity.md) is complete with conclusion:

**A — EXISTING AUTHORITY MODEL SUFFICIENT; BOUNDED RUNTIME HARDENING
REQUIRED.**

This roadmap derives five bounded phases from evidence. It is direction, not
authorization. No new phase starts without explicit user approval. v0.6
remains an internal milestone; no v0.6.0 RC, tag, version bump, package, or
public release is planned.

## 2. Architectural boundary

The existing authority epoch remains:

```text
RuntimeSessionId
+ ApplicationGenerationId
+ exact BackendLocator
+ current InteractionScope/capability/public state
```

No new runtime epoch ID, window manager, surface generation, task engine,
workflow system, event log, or application/toolkit adapter is planned.

## 3. Phase 0.6A — Runtime Epoch and Late-Work Isolation

**Status: COMPLETE / VALIDATED.** See the
[0.6A validation handoff](../validation/v0.6/runtime-epoch-late-work/HANDOFF.md).

**Core runtime question:** Does every asynchronous or bounded operation lose
the ability to publish mutation, confirmation, artifact, or status after its
application generation is invalidated?

Validated scope:

- inventory and bind every operation/task completion to the existing ticket;
- require current ticket completion for external-text final success;
- make cancellation and stale completion results consistent;
- retain current exact-locator/scope/capability revalidation;
- cover operation versus target loss, app exit, restart, and shutdown.

Explicit exclusions:

- new epoch identity;
- semantic retries;
- new interaction capabilities;
- task/session frameworks.

Completed live evidence:

- blocked action across app restart;
- cancelled late operation result;
- external text return across target/app replacement;
- fresh current operation remains usable afterward.

Exit condition: no work owned by G1 can mutate, confirm, publish, or overwrite
state in G2, and cancellation completes within an explicit bound.

## 4. Phase 0.6B — Transport and Application Recovery

**Status: COMPLETE / VALIDATED.** See the
[0.6B validation handoff](../validation/v0.6/transport-application-recovery/HANDOFF.md).

**Core runtime question:** Can AT-SPI loss and application disappearance fail
safely and recover through a fresh generation without name-based semantic
reauthorization or non-idempotent replay?

Validated scope:

- separate transport reconnection from application reauthorization;
- make duplicate-name recovery unambiguous or require user selection;
- retain bounded backoff and explicit F5 recovery;
- qualify A-to-B app selection and no-app-to-fresh-app behavior;
- clarify concise unavailable/recovered UX.

Explicit exclusions:

- process supervision;
- automatic same-name app resume;
- multi-app automation;
- deployment/Wayland/SSH support work;
- blind action replay.

Completed live evidence:

- real AT-SPI daemon loss and return inside an isolated session;
- duplicate/same-name app replacement;
- distinct app A-to-B selection;
- old locators, commands, events, and tickets refused;
- new generation and fresh action available.

Exit condition: supported transport recovery either establishes fresh explicit
application authority or remains safely unavailable; it never guesses the app
or replays a non-idempotent operation.

## 5. Phase 0.6C — Surface, Event, Cache, and Resource Continuity

**Core runtime question:** Do repeated current-surface transitions remain
correct while every long-lived queue, task, cache, and UI-history structure is
explicitly owned and bounded?

Authorized future scope:

- explicit event producer shutdown/ownership;
- bounds or pruning for scope focus history and command recency;
- queue-overflow resync continuity;
- repeated window/modal/menu lifecycle;
- contents-free resource observations for cache nodes, tasks, tickets, FDs,
  artifacts, and memory.

Explicit exclusions:

- performance optimization campaign;
- window manager or surface registry;
- semantic scrolling;
- exhaustive virtualization;
- application/toolkit branches.

Required live evidence:

- same-process W1-to-W2 and simultaneous-window scope;
- unique-surface churn sufficient to exercise history pruning;
- repeated overflow followed by successful fresh operations;
- old producer/event cannot affect the current generation;
- bounded cache/task/FD/artifact observations.

Exit condition: churn cannot retain stale authority or grow owned historical
state without a documented bound, and fresh current bindings remain usable.

## 6. Phase 0.6D — External and Terminal Lifecycle

**Core runtime question:** Do configured external interactions, modality work,
temporary artifacts, signals, and terminal ownership cleanly survive or stop
across lifecycle transitions?

Authorized future scope:

- preserve 0.6A final-ticket enforcement while qualifying broader external
  text/modality cancellation and lifecycle cleanup;
- success/refusal/cancel/shutdown artifact cleanup and startup recovery;
- normal exit, SIGINT/SIGTERM, detach/reattach, resize, and controlled panic;
- explicit decision on SIGTSTP/SIGCONT support.

Explicit exclusions:

- new external modality types;
- remote transport;
- shell-command guessing;
- deployment matrix;
- crash-recovery framework.

Required live evidence:

- long bounded handler with target/app replacement;
- exit during external/capture work;
- artifact and FD counts after repeated cycles;
- terminal mode restoration for every supported path;
- honest documented outcome for suspend/resume.

Exit condition: no external result reaches a stale target, owned resources
have explicit cleanup/recovery, and the terminal returns to a usable state for
all declared supported exits.

## 7. Phase 0.6E — Integrated Runtime Continuity Qualification

**Core runtime question:** Do the qualified v0.1-v0.5 guarantees remain
correct over a bounded mixed lifecycle workload?

Authorized future scope:

- a small cycle-based corpus using existing Action, Text, Selection,
  PageTab/Expand, modal, and external-text operations;
- app generations, surface churn, event pressure, one transport interruption,
  cancellation, and resource sampling;
- one final v0.6 source-quality and Linux live qualification;
- milestone functional handoff.

Explicit exclusions:

- new interaction families;
- compatibility app-count targets;
- hour-scale arbitrary benchmarks;
- v0.7 environment qualification;
- RC/tag/release work.

Required live evidence:

- stale authority and late work remain isolated;
- recovery follows the qualified policy;
- no duplicate non-idempotent action;
- event/resource bounds hold;
- fresh existing tasks remain usable;
- terminal and external cleanup pass.

Exit condition: the v0.6 exit definition passes with P0 = 0 and P1 = 0 and
no new runtime/task subsystem.

## 8. Proposed milestone exit definition

v0.6 functional development completes when established semantic and task
guarantees survive the agreed application, transport, window/surface, event,
operation, external-handler, resource, and terminal lifecycle transitions
without authority migration, stale-result corruption, false event truth,
unbounded retained runtime state, unsafe automatic replay, or terminal/resource
stranding. The runtime must reacquire fresh authority or fail safely according
to its explicit supported recovery contract.

Milestone qualification remains a separate user-authorized close after all
functional phases. v0.7 and 1.0 remain unchanged.
