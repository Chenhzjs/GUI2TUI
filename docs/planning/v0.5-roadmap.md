# GUI2TUI v0.5 — Task & Interaction Completeness Roadmap

Status: **DISCOVERY COMPLETE / IMPLEMENTATION NOT AUTHORIZED**  
Discovery conclusion: **A — TASK-COMPLETENESS MILESTONE JUSTIFIED**  
Detailed evidence: [v0.5 Task & Interaction Completeness Discovery](v0.5-task-interaction-completeness.md)

This roadmap derives bounded implementation phases from user-task blockers.
It is direction, not authorization. A phase starts only after explicit user
approval, closes with its own evidence, and stops before the next phase.

## 1. Milestone question and fixed foundation

**Question:** Can ordinary desktop interaction families complete a bounded,
useful generic task baseline through public Accessibility semantics?

v0.5 extends the existing capability pipeline; it does not create a task
engine:

```text
fresh current SceneBinding
  -> explicit task-relevant UiIntent
  -> exact SemanticOperation / BackendOperation
  -> public Accessibility operation
  -> authoritative target-specific readback
  -> v0.4 transition, scope, realization, and current-scene rebuild
  -> user manually chooses the next step
```

All v0.1–v0.4 invariants remain fixed. In particular, method acceptance,
events, focus, visibility, names, indices, geometry, timing, and retained
`RuntimeNodeId` never substitute for exact current authority and fresh
semantic truth.

## 2. Agreed common-task baseline

v0.5 should qualify these generic tasks when sufficient public semantics
exist:

- complete a common structured form and supported dialog;
- invoke ordinary named Buttons, links, standard menus, and supported nested
  menu commands;
- select one exact current list item or Table row with authoritative readback;
- switch a public page tab and continue from the current page;
- reveal a hierarchy item through an explicit qualified semantic operation and
  continue through current public structure;
- Open a file and Choose a folder through exact current chooser semantics;
- read and navigate current list/table/content surfaces while preserving
  partial/virtualized honesty.

This baseline does not require arbitrary multi-selection, Save As overwrite,
exhaustive virtualized traversal, pointer-only context menus, drag and drop,
universal widget coverage, or automatic task completion.

## 3. Dependency order

```text
0.5A verified current collection selection
  ├─ enables list/table tasks
  ├─ supplies exact chooser row targeting
  └─ supplies one public page-tab operation shape

0.5B hierarchy reveal and page continuation
  ├─ reuses 0.4A transition observation
  ├─ reuses 0.4C realization/manual continuation
  └─ completes navigation across hierarchical and paged task surfaces

0.5A + 0.5B + v0.4
  -> 0.5C Open-file and Choose-folder tasks

0.5A–0.5C
  -> 0.5D integrated common-task baseline qualification
```

## 4. Phase 0.5A — Verified Current Collection Selection

**Core task question:** Can the user choose one exact current item or Table row
without a stale index, a method-return boolean, focus, or an item Toggle being
mistaken for authoritative selection truth?

### Authorized future scope

- qualify exact current single selection through parent Selection or an exact
  compatible child action;
- add target-specific fresh selected-child/Selected-state readback;
- re-resolve any index from the chosen current locator immediately before
  invocation;
- add Table row selection and exact selected-row/current-cell verification
  where Table semantics are public;
- prevent null/defunct, reordered, replaced, hidden, out-of-scope, or
  unrealized targets from producing success;
- correct false Complete/interactive collection affordances where current
  public semantics cannot establish completeness;
- reuse `SemanticCapability`, `UiIntent`, `SemanticOperation`,
  `BackendOperation`, `SceneBinding`, v0.4 authority, and existing Choice UI.

### Explicit exclusions

- arbitrary multi-selection, select-all, selection ordering, and range
  selection;
- automatic scrolling or targeting of unrealized items;
- table editing, column manipulation, or a collection subsystem;
- app/toolkit branches, names as identity, fuzzy rebinding, or input injection;
- Choice replacement or a persistent selection session.

### Required live evidence

- GTK-style parent Selection: exact before, operation, exact selected-child
  readback, and fresh current binding;
- Qt-style exact item action: selected-state readback without assuming a
  parent Selection interface;
- GTK-style Table row selection: Table row operation/readback, not flattened
  `SelectChild` guessing;
- dynamic reorder/replacement or deterministic equivalent: old index/locator
  cannot select a replacement;
- virtualized out-of-window case: accepted/null or unverifiable result refuses;
- one fresh selected item can perform an already-supported next operation,
  with the user controlling the step.

### Exit condition

One exact current item or Table row is selectable through generic public
semantics and authoritative readback; stale/reordered/unrealized ambiguity
cannot create success; current Choice behavior and v0.4 authority do not
regress; P0 = 0 and P1 = 0.

## 5. Phase 0.5B — Hierarchy Reveal and Page Continuation

**Core task question:** Can the user reveal current hierarchy content or
switch a page when the application exposes a verifiable semantic operation,
then continue manually through the refreshed scene?

### Authorized future scope

- qualify user-facing Expand/Collapse only for exact compatible advertised
  action plus authoritative Expanded readback;
- refuse Expandable controls whose advertised action does not establish the
  requested state;
- qualify PageTab switching through parent Selection or exact compatible Tab
  action with a fresh public current-page post-state;
- reuse v0.4 transition observation, realization, scope, focus, scene, and
  manual continuation;
- expose minimal current TUI intents/help only for qualified current controls.

### Explicit exclusions

- recursive expansion, automatic descendant search, automatic first-child
  focus, tree selection breadth, or a TreeNavigator;
- mapping arbitrary Toggle to Expand;
- inferred trigger/descendant ownership or hierarchy from names/geometry;
- tab workflow/session objects, terminal navigation redesign, or task
  automation;
- virtualized exhaustive hierarchy traversal.

### Required live evidence

- GTK disclosure with exact expand/collapse actions, Expanded readback,
  sibling realization, and no ownership inference;
- a true descendant realization using fresh public structure where available;
- a negative Qt-style Expandable + Toggle case that remains unsupported when
  Expanded does not change;
- GTK TabList Selection and Qt PageTab Action shapes, each with authoritative
  current-page evidence rather than focus alone;
- stale tab/realized-child bindings refuse after the page or hierarchy changes;
- Tab/F6/Ctrl+Tab/RegionNavigator behavior remains the existing terminal
  navigation model.

### Exit condition

Hierarchy reveal and page switching work for explicitly qualified public
semantics, unverifiable controls expose no false affordance, v0.4 produces the
fresh current scene, and the user manually continues without a hierarchy or
page subsystem; P0 = 0 and P1 = 0.

## 6. Phase 0.5C — File and Folder Choice Tasks

**Core task question:** Can a user Open an existing file and Choose a folder in
an accessible chooser using exact current semantic targets, without reading or
mutating backing state directly?

### Authorized future scope

- complete Open-file and Choose-current/reachable-folder workflows on
  evidence-backed accessible choosers;
- use qualified current collection/Table selection, current public location
  evidence, exact row/cell activation where semantically compatible, exact
  confirmation actions, and v0.4 modal/transition continuation;
- distinguish public type/location evidence from absent or ambiguous evidence;
- use synthetic temporary files/directories for validation;
- provide concise safe refusal when file/directory identity, location,
  selection, traversal, or completion cannot be established.

### Explicit exclusions

- a FileChooser framework or private GTK/Qt APIs;
- backing-file mutation, filesystem inspection as GUI truth, filename-suffix
  type guessing, icons/geometry as type, double-click/Enter injection;
- arbitrary Save As overwrite handling unless separately authorized after
  additional evidence;
- exhaustive virtualized directory traversal, recent-location completeness,
  remote protocol support, or application-specific chooser handling;
- multi-selection and bulk file operations.

### Required live evidence

- synthetic Open: current location, exact file-row selection and readback,
  exact confirmation, dialog disappearance, and application-visible result;
- synthetic Choose Folder: current/reachable folder semantics, exact
  confirmation, and application-visible result;
- directory traversal: exact semantic operation, current breadcrumb/listing
  change, fresh bindings, and stale old listing refusal;
- absent file/directory type case: no invented type or unsafe target;
- modal background confinement and return through existing v0.4 architecture;
- at least one second implementation or real chooser if readily available;
  otherwise document safe implementation limits without toolkit branches.

### Exit condition

Open and Choose Folder complete through generic exact public semantics where
available, ambiguity refuses without guessing, no backing-state bypass or
chooser subsystem exists, and v0.4 owns all dynamic continuation; P0 = 0 and
P1 = 0.

## 7. Phase 0.5D — Common Task Baseline Qualification

**Core task question:** Do forms, dialogs, collection selection, tabs,
hierarchy reveal, menus, and bounded file/folder choice now form one coherent
task-first product model without false capability?

### Authorized future scope

- integrated user-level qualification of the agreed baseline;
- minimal task-oriented help/status/command corrections only when a real
  workflow is misleading;
- representative regression of v0.1 semantics, v0.2 presentation, v0.3
  verified mutation, and v0.4 continuation;
- final v0.5 documentation and internal Milestone Qualification.

### Explicit exclusions

- new interaction family, multi-select breadth, Save As overwrite, exhaustive
  virtualization, context-menu injection, workflow UI, task planner, v0.6,
  release/version/tag/package work;
- app count, role count, widget count, or test count as success metrics.

### Required live evidence

- one structured form from field edits through submit/result;
- one exact list choice and one Table-row task;
- one page switch and one hierarchy reveal with manual continuation;
- standard/nested named menu command regression;
- Open file and Choose Folder on synthetic content;
- stale/reordered/unrealized/ambiguous negative paths with no false success;
- current terminal navigation, Reader, Choice, Value, Text, complex text,
  password exclusion, modal confinement, and external modality remain intact.

### Exit condition

Every baseline task completes or degrades through an explicitly documented
safe result; no false selection, hierarchy, completeness, or continuation
claim remains; production stays generic; final Linux live evidence and the
normal milestone-close source/docs quality matrix pass once; P0 = 0 and
P1 = 0.

## 8. v0.5 milestone exit definition

v0.5 is **COMPLETE / MILESTONE QUALIFIED** only when:

1. common forms and supported dialogs complete without special frameworks;
2. exact current single item/Table-row selection has authoritative readback;
3. stale, reordered, replaced, null, or unrealized selection cannot succeed;
4. qualified hierarchy reveal uses exact public action and Expanded truth;
5. qualified page switching establishes a public current-page result;
6. Open-file and Choose-folder tasks complete where sufficient public
   semantics exist and refuse otherwise;
7. public structure, scope, generation, exact locator, visibility, and fresh
   bindings remain operation authority;
8. v0.4 owns dynamic transition/surface/realization continuation;
9. partial and virtualized content is never claimed complete without evidence;
10. multi-selection, Save As overwrite, exhaustive virtualization, and
    pointer-only tasks remain honest explicit boundaries unless later
    separately authorized evidence changes them;
11. no application/toolkit branch, private API, injected input, coordinates,
    anonymous action, fuzzy identity, inferred hierarchy, task session, or
    workflow engine is introduced;
12. relevant Linux live evidence, representative prior-layer regression, and
    milestone-close source/docs quality pass with P0 = 0 and P1 = 0.

## 9. Deferred work and milestone boundaries

- Multi-selection set breadth, Save As overwrite, exhaustive virtualized
  traversal, pointer-only context menus, drag/drop, and universal task
  compatibility are not required by this roadmap.
- v0.6 retains long-running runtime continuity, reconnect, restart,
  multi-application lifecycle, event backpressure, resource, and soak work.
- v0.7 retains installation, permissions, Wayland/SSH/environment, deployment,
  and support-contract work.
- v0.5 remains an internal milestone. No `v0.5.0` package version, RC, tag,
  artifact campaign, or public release is planned.
- v1.0.0 remains the next planned public release under the current policy.
