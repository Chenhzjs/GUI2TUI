## 2. Executive finding

- The highest-value gap is complex text mutation: v0.2 can atomically replace
  verified plain single-line inputs, but multiline/rich/code/document text is
  only readable (often partial) and has no safe public whole-document write
  contract.
- The gap is not “all Unsupported controls should become editable.”  Several
  controls are structurally or fidelity-only, and several advertised
  interfaces are incomplete, rejected, or unreliable in real applications.
- Small structured controls already have the right terminal shape: explicit
  Action, parent Selection, and the Choice overlay work for GTK/Qt/Firefox
  evidence.  The next native targets should be only operations with a bounded
  value domain and authoritative readback.
- AT-SPI 0.30 exposes more than GUI2TUI currently consumes: Value setters and
  bounds, Text caret/range selection, Selection deselection/multi-select, and
  Table row/column selection are available in the dependency, but are not
  semantic operations in this release.
- Public capability is not sufficient by itself.  Firefox accepted
  `EditableText.SetTextContents` but its independent read-back stayed
  unchanged; Qt 6.4 crashed while serving a Text read; Chrome exposed
  anonymous actions and a hidden Selection parent that rejected selection.
- Existing generation identity, event invalidation, authoritative read-back,
  and owned private artifacts provide most of the safety substrate needed for
  future recovery.  There is no general `OperationRegistry` or operation-trust
  model yet; only the runtime ticket map and Text-specific quarantine exist.
- A low-coupling configurable interaction handler is technically plausible for
  complex non-secret text, but it must exchange a GUI2TUI-owned representation,
  never the application’s backing file, and must write back only through public
  AT-SPI followed by verification.
- The recommended architecture is hybrid: native bounded structured controls,
  a small argv-based external handler boundary for complex free-form content,
  and explicit safe degradation everywhere else.

## 3. Current Unsupported/read-only architecture

The semantic pipeline is `AT-SPI → SemanticCache → regions/content → TuiScene`
and `SceneBinding → SemanticOperation → BackendOperation → AT-SPI`.  A generic
`SemanticCapability` currently contains only `SelectChildren` and `EditText`
(`src/semantic/node.rs`), while `InteractionCapability` maps the supported
terminal intents (`src/tui/action.rs`).

Unsupported/read-only is produced at several distinct layers:

1. **Acquisition/validation.** `BackendError` distinguishes missing AT-SPI
   interfaces, no actions, stale objects, selection rejection, unsupported
   text, password refusal, non-advancing ranges, timeouts, and application
   rejection (`src/backend/atspi.rs`).
2. **Capability derivation.** `semantic_capabilities` advertises
   `SelectChildren` for an AT-SPI Selection interface and `EditText` only for a
   plain, non-password, editable, single-line TextInput with both Text and
   EditableText.  Multiline is deliberately excluded because atomic replacement
   would target a document buffer.
3. **Operation resolution.** `resolve_action` requires a role-compatible
   advertised name; it never uses anonymous actions or index zero.  Selection
   resolves to a named child action or a parent Selection child index.  Text
   replacement resolves only from an EditText SceneBinding.
4. **Choice analysis.** `ChoiceCatalog` returns `Unavailable` when named
   options or a safe child-action/visible-parent-Selection strategy is absent.
   It does not open a GUI popup merely to reconstruct options.
5. **Content runtime.** Text sources move through `Unsupported → Declared →
   Verified` or `Quarantined`.  A failed bounded read is not retried in the
   same generation; unavailable blocks remain honest Reader placeholders.
6. **Presentation.** `SceneElementKind::Unsupported`, read-only suffixes,
   `Structural`, `DiagnosticOnly`, `PreserveModality`, and compact unavailable
   notices are presentation outcomes.  They do not revoke or create backend
   capability.  Opaque graphical surfaces use a fidelity-preserving modality,
   not a fake interactive widget.
7. **Runtime/lifecycle.** Missing applications, endpoint loss, object churn,
   event overflow, cancellation, and generation replacement discard active
   state.  Old locators, RuntimeNodeIds, Scene bindings, and operation tickets
   are rejected rather than reconciled across an application restart.

This explains why one word such as “Unsupported” is currently overloaded: it
can mean no semantic operation, an intentionally disqualified capability, an
unreliable probe, an application rejection, incomplete realization, or a
presentation-only structural surface.

## 6. Text capability findings

**Single-line.** The current boundary is evidence-backed rather than a role
guess: plain TextInput, Text + EditableText, editable state, non-password, and
not MultiLine. `EditSession` keeps a Unicode-scalar cursor and blocks commit on
external change. `SetTextContents` is followed by event settling, an independent
full read, and node refresh. GTK and Qt passed; Chrome was read-only; Firefox
demonstrated why the boolean return is not proof of success.

**Multiline.** Text/EditableText can be present, but `MultiLine` deliberately
removes `EditText`. GTK TextView is readable through bounded ranges; Qt 6.4
QTextEdit crashed during a Text read and is quarantined for that generation.
The existing Reader is the safe product behavior. A future external handler
must not receive a source file or claim full-document completeness from a
partial model.

**Document/rich text.** Document, Text, Hypertext, attributes, headings,
links, and bounded paragraphs are readable. Writer long documents are
`PartialRealized`; rich attributes and atomic formatting writes are not modeled.
The safe external representation, if later approved, is an explicitly named
projection (for example plain text) with loss acknowledged, not a silent rich
document round-trip.

**Browser fields.** Chrome exposed a Text entry without EditableText and one
probe had no printable value. Firefox exposed EditableText but rejected the
effective write on read-back. No keyboard injection or DOM/CDP fallback is
architecturally acceptable.

**Password.** PasswordText is excluded before Text reads, content modeling,
editing, external materialization, and normal/log output. This remains an
absolute boundary.

**Electron/code editor.** VS Code/Electron discovery and Reader/search work
best-effort; anonymous Manage actions and Monaco editing remain refused. No
application-specific bridge is justified by current evidence.

## 7. Structured capability findings

- **Value:** AT-SPI `Value` is imported and read for Slider/ProgressBar/
  LevelBar/SpinButton (`text`, then `current_value`), but no setter is called,
  no value capability is represented, and Slider page navigation in Writer is
  safely cancelled. This is a plausible high-value native target only after
  range/increment and read-back behavior are surveyed.
- **Selection:** Explicit child actions and visible parent Selection already
  work. Deselect, clear, select-all, selected-child enumeration, and
  multi-selection are absent from the semantic operation model.
- **Choice:** The terminal overlay is mature and should be extended only by
  evidence-backed strategies. Unnamed options and hidden/rejecting parents
  remain read-only.
- **Expand/collapse:** Expanded/Collapsed state is retained; generic operation
  resolution has no expansion action family and no wait-for-realization
  sequence. This is a compound-operation candidate, not a key-sequence task.
- **Tables/cells:** `TableProxy` probes dimensions and realized cells; the
  table model navigates realized cells and never fabricates totals. Cell
  editing and row/column selection are not represented.
- **Other:** Hypertext/Hyperlink and Document metadata are read-only evidence;
  opaque media belongs to resource modality, not semantic editing.

## 8. Native vs external decision criteria

Choose Native TUI when the interaction is small, structured, role-appropriate,
bounded by explicit public capability, and has a direct authoritative state
read-back. Choose an external configurable handler when the payload is large or
free-form, human editing benefits from a mature local modality, the exchanged
representation can be bounded and non-secret, and GUI2TUI can still perform the
public write-back and verification. Remain Unsupported when capability is
missing, anonymous, partial without a safe target, privacy-sensitive, rejected,
or not verifiable.

Across all three choices, weigh: operation complexity, data size and duration,
structured versus free-form semantics, terminal affordance, cursor/range or rich
editing needs, atomic public operation availability, verification quality,
sensitivity, scope/generation lifetime, and conflict behavior. Application
names and toolkit identity are never criteria.

## 10. Configurable external interaction handler

An external handler is recommended only for a future, explicitly authorized
complex-text phase. The concept should be generic (`ExternalInteractionHandler`
or `EditableResourceHandler`), not `$EDITOR`-centric and not an application
adapter.

**Conceptual contract.** GUI2TUI would provide a bounded, GUI2TUI-owned
representation descriptor: semantic operation class, media type/projection,
display label, generation/target token, starting fingerprint, and payload. A
handler returns an explicit outcome (`cancelled`, `unchanged`, `modified`, or
`failed`) plus a bounded result. The handler never receives a BackendLocator,
application path, password, or remote descriptor.

**Transport.** A private temporary file is the most compatible first candidate
for large text because it supports mature local editors without a shell. stdin/
stdout is attractive for small values but makes interactive terminal ownership,
size limits, exit/cancel semantics, and binary-safe framing harder. A managed
artifact is useful as an ownership/lifetime primitive, but existing modality
artifacts are view-oriented and must not be treated as an application backing
file.

**Configuration.** Extend the existing XDG TOML concept minimally, for example
`[interaction_handlers]` with operation-class or media-type keys whose values
are argv arrays. Do not accept shell command strings or remote-provided paths.
Handler availability is checked locally; a missing handler leaves the control
read-only. Fallback order should be explicit configured match, then no handler;
`VISUAL`/`EDITOR` may be an opt-in convention outside the core contract, never a
required fixed dependency or hardcoded program name.

**Lifecycle and security.** Reuse `OwnedArtifactDirectory` conceptually and
its 0700/0600 ownership, lease, bounded-file, crash-recovery, and cleanup
properties. Tie the interaction to a RuntimeSession operation ticket and
ApplicationGenerationId. On cancel/failure, preserve the user result only in a
private recovery location if explicitly requested; otherwise remove it. Never
export PasswordText or any value that was not safely read. Handler exit status
means only handler completion; GUI acceptance still requires a public write and
read-back.

## 11. Relationship to External Modality

**Reuse directly:** private XDG/runtime paths, `OwnedArtifactDirectory`, local
argv process spawning pattern (after adapting it to an interactive lifecycle),
authorization prompts/policy concepts, bounded descriptors, cancellation,
endpoint/generation ownership, redacted diagnostics, and cleanup/reaping.

**Reuse conceptually:** reference-first resolution, explicit local user policy,
handler capability negotiation, and separation of semantic source from local
modality.

**Keep separate:** `ExternalModality` resource variants and `LocalModalityBroker`
are primarily for opening/viewing references or one-shot artifacts. An
interaction handler mutates a semantic target, needs conflict detection and
write-back verification, and must not be confused with a viewer accepting an
artifact. Do not make a modality provider the semantic tree source and do not
reuse a resource URI as an editable application file.

The low-coupling principle transfers: local handler paths are user-owned, never
remote descriptors; payload transfer is bounded and authorized; provider
capability does not create GUI capability. Mutation ownership and verification
do not transfer mechanically from visual modality.

## 12. Authoritative write-back model

Future writes should follow one operation-specific contract:

1. Capture current semantic target, generation, locator, relevant state, and a
   starting value/fingerprint.
2. Resolve an explicitly advertised compatible public operation in the current
   Scene/Cache and active InteractionScope.
3. Invoke the AT-SPI method/action with a bounded timeout and operation ticket.
4. Consume relevant events opportunistically; events are hints, not authority.
5. Re-read the authoritative property/content through the public AT-SPI
   interface and refresh the target node/subtree.
6. Report confirmed, normalized, rejected, unavailable, stale, or unverified
   outcome. Never install optimistic state as truth.

Verification is generic in shape but operation-specific in evidence: text reads
text; toggle reads Checked/Pressed; selection reads Selected or selected child;
Value reads CurrentValue; expand reads Expanded and confirms child realization.
An operation that cannot define a meaningful read-back remains unsupported.

## 13. Conflict/stale handling

The minimal future model is compare-before-write plus safe refusal. Store
`RuntimeSessionId`/`ApplicationGenerationId`, exact `BackendLocator`, starting
semantic value (or bounded content fingerprint), and any available state/version
signal. During a long external interaction, events or a fresh read mark the
target changed. Before write-back, require the same generation, locator, and
starting fingerprint; otherwise refuse overwrite and retain the edited result
only in the private handler result area for explicit user review. Do not build a
merge engine. Application restart, target removal, ambiguous reconciliation,
handler timeout, or endpoint loss cancels the write and invalidates the result
ticket.

The existing `EditSession.external_change_detected`, locator checks, runtime
ticket rejection, and generation invalidation are a strong starting point, but
the current source-generation field is a plain numeric cache generation and is
not yet a general content fingerprint contract.

## 14. Trust/quarantine

Current trust is narrow and useful: `TextCapabilityStatus` is
`Unsupported/Declared/Verified/Quarantined`; failed bounded reads quarantine a
source for the current generation, and a new generation re-evaluates it.
Action/Selection operations instead rely on explicit role-compatible names and
backend acceptance; there is no persisted `Declared/Verified/Rejected` action
state. Runtime tickets and modality authorization are separate ownership
mechanisms. No `OperationRegistry` type exists; `RuntimeSession.operations` is a
bounded ticket map.

Recommendation: keep Text read trust separate from mutation authorization and
from external-handler trust. Add the smallest operation-specific evidence state
only if Phase 0.3 discovery demonstrates repeated declared-but-unsafe methods.
Prefer per-interface/operation and generation-scoped observations over
application-name or global bans. Do not create a generalized trust framework in
discovery.

## 15. Compound semantic operations

Some recovery candidates need a bounded sequence: open/observe a semantic popup,
wait for children, select, then verify; or expand, wait for realization, select,
and verify. Existing machinery can represent the first half (individual
`SemanticOperation`s plus event-driven refresh), but it has no transaction,
deadline, intermediate-scope, or compensation contract. A future
`CompoundSemanticOperation` may be justified only if one such sequence is
demonstrated across more than one generic role and cannot be expressed as a
single public operation. It must never become keyboard/mouse scripting or
anonymous action sequencing. Until then, implement operation-specific bounded
orchestration around existing operations rather than presupposing a new IR type.

## 16. Architecture options

| Option | Complexity | Coupling | Correctness/security | UX | Infrastructure reuse | Maintenance |
| --- | --- | --- | --- | --- | --- | --- |
| A. Mostly native | High as soon as multiline/rich/range/value families grow; every editor needs terminal semantics | Low to applications, high to many AT-SPI edge cases | Strong for bounded controls; weak where public write/read-back is incomplete; secrets can remain excluded | Excellent for small controls, poor for rich/free-form editing | Reuses SemanticOperation and Scene directly; little modality reuse | Large surface area and repeated editor semantics |
| B. Hybrid native structured + configurable handler | Moderate; native additions stay bounded and handler boundary is small | Low if handler receives only GUI2TUI-owned representations | Best balance: public capability/read-back remains authoritative; private artifacts and argv handlers are controllable | Native controls feel native; complex text uses user’s chosen local modality | Reuses runtime tickets, artifacts, XDG config, authorization concepts; keeps resource modality separate | One handler lifecycle and representation contract to maintain |
| C. Externalize most interaction | Initially low product code, but broad handler protocol and policy burden | Highest: behavior depends on local programs and representations | Weakest; temptation to pass backing paths or bypass AT-SPI write-back | Inconsistent and poor for checkboxes, choices, and modal tasks | Heavy modality/broker reuse, but semantic operation layer becomes thin | Protocol/security compatibility and UX fragmentation |

Only A and B are credible under the evidence. C would make GUI2TUI a launcher/
automation shell and conflicts with semantic ownership.

## 17. Recommended v0.3 architecture

Recommend **Option B: bounded native structured operations plus a low-coupling
configurable interaction handler for complex non-secret representations**.

This preserves the strongest existing path (named actions, Choice, Selection,
authoritative read-back), addresses the practical multiline/free-form gap without
pretending a terminal editor is a document engine, and reuses private artifact
and runtime ownership without conflating resource viewing with state mutation.
The handler is optional; no configured handler means honest read-only behavior.
The original GUI remains the only authority, and every write is refused unless
public capability, current identity, conflict checks, and operation-specific
verification all pass.

## 18. Proposed v0.3 phases

These are derived planning phases, not started work.

### Phase 0.3A — Capability evidence and operation contracts

Goal: turn the taxonomy into reviewed, operation-specific capability evidence
and verification rules without changing product behavior first.

Scope: targeted probes for Value setter/read-back, Text caret/ranges,
Selection deselection/multi-select, expand/realization, and representative
text payload fingerprints; define safe outcomes and trust transitions.

Non-goals: no new public enum/API commitment, no external handler, no input
injection, no app-specific rule.

Validate: GTK/Qt fixtures, Firefox/Chrome choices and fields, Writer slider/
document, Qt/GTK multiline fixtures.

Hard success: each candidate has evidence-backed preconditions, invocation,
read-back, timeout, stale/conflict, and safe-failure rules—or is explicitly
deferred.

### Phase 0.3B — Native bounded structured recovery

Goal: recover the highest-value small controls whose public operations are
explicit and verifiable.

Scope: only evidence-approved Value and/or selection/expand families, preserving
existing Action/Choice behavior and active scopes.

Non-goals: multiline/rich editing, anonymous actions, password, table-cell
editing, compound key scripts.

Validate: GTK/Qt controls, Firefox visible Selection, Writer Options/slider,
Qt Designer choice/settings.

Hard success: no optimistic state; every accepted write has authoritative
read-back and safe rejection across at least two generic role/toolkit families.

### Phase 0.3C — Configurable non-secret text interaction

Goal: provide an optional handler boundary for complex plain/structured text.

Scope: GUI2TUI-owned bounded representation, argv handler configuration,
private artifact lifecycle, cancel/failure outcomes, generation/fingerprint
conflict refusal, AT-SPI write-back and read-back.

Non-goals: `$EDITOR` requirement, backing-file edits, rich-format fidelity,
password export, remote handlers, plugin SDK/marketplace, DOM/CDP/UNO.

Validate: Mousepad/GTK TextView, Qt multiline only where safe, Writer exposed
text, Firefox/VS Code only if public writable semantics are demonstrated.

Hard success: a changed non-secret representation can be cancelled, returned,
refused on conflict, written only through AT-SPI, and confirmed or honestly
reported unverified; handler failure leaves GUI unchanged.

### Phase 0.3D — Compound operations and UX qualification

Goal: add only proven generic multi-step operations and user-facing cause
distinctions.

Scope: one or two evidence-backed sequences, diagnostics retaining detailed
causes, concise distinctions such as “editing unavailable”, “application
rejected”, and “external handler available”.

Non-goals: broad compatibility campaign, full release qualification, merge
engine, or presentation-driven capability invention.

Hard success: scope, deadlines, cancellation, stale identity, and intermediate
read-back are deterministic in real workflows.

## 19. Priority order

1. Preserve and document the existing plain single-line verified edit path and
   its Firefox/Chrome safe degradation (high value, already low risk).
2. Investigate small Value/SpinButton/Slider mutation (high practical value in
   settings-heavy Writer/Designer workflows; bounded if read-back works).
3. Investigate non-secret multiline plain text representation and handler
   round-trip (high user value, but only after conflict/security evidence).
4. Improve explicit Selection/choice coverage where public parent/child
   semantics are already visible; add deselection only if real use cases and
   verification are demonstrated.
5. Consider expand/collapse compound orchestration after named actions and
   child realization are observed generically.
6. Defer rich/code editing, table-cell writes, anonymous browser actions,
   hidden/rejecting selections, and graphical/live surfaces until evidence
   changes their safety classification.

The order reflects user value, generic applicability, safety, and feasibility,
not novelty or the mere existence of an AT-SPI method.

## 20. Explicit non-goals

- No DOM/CDP, UNO, private toolkit APIs, OCR/vision, screenshot semantics, or
  framebuffer reconstruction.
- No keyboard/mouse injection, coordinate clicking, XTest/uinput, scripted key
  sequences, or anonymous action/index guessing.
- No application-specific adapters or branches for Mousepad, browsers,
  Electron, Writer, Designer, or toolkit identity.
- No fixed external editor dependency and no requirement for `$EDITOR` or
  `$VISUAL`.
- No direct backing-file/database edits, path handoff to an application editor,
  or claim that a handler is the semantic backend.
- No password/secret export, external artifact, logging, or editing.
- No broad plugin SDK, dynamic-library system, RPC marketplace, remote handler,
  or cross-host transport unless a later review authorizes it.
- No full merge engine, rich-format fidelity promise, large benchmark, release
  qualification, or new test suite in discovery.

## 21. Risks / open questions

- Which AT-SPI implementations provide stable, verifiable Value setters and
  Text range/caret operations across generic roles?
- Can a multiline text projection preserve enough identity and completeness to
  make a safe external round-trip, especially for partial Writer/browser
  trees?
- What bounded temporary-file size and lifetime are acceptable for interactive
  handlers, and how should an explicitly preserved failed result be surfaced?
- Is a shell-free argv handler sufficient for terminal ownership, cancellation,
  and result signaling, or is a small framed stdin/stdout mode needed later?
- Can operation-specific trust observations be added without creating a global
  per-application quarantine list?
- Which expansion/selection sequences are truly generic and which applications
  merely expose misleading actions?
- How should user-facing wording distinguish “not exposed”, “not verified”,
  “application rejected”, and “handler unavailable” without leaking low-level
  D-Bus details?
