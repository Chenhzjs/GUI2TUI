# GUI2TUI v0.4 Roadmap — Bounded Semantic Continuation

This roadmap is derived from the completed
[v0.4 Discovery](v0.4-workflow-reconstruction.md). It is direction, not
authorization. No phase starts without explicit user approval.

## Status and decision

- **Discovery — COMPLETED**
- **Architecture conclusion — B. NARROWER CONTINUATION MODEL SUFFICIENT**
- **0.4A — RECOMMENDED / AWAITING USER AUTHORIZATION**
- **0.4B–0.4D — PLANNED / NOT AUTHORIZED**

v0.4 does not need a workflow engine. Existing event refresh, scene rebuild,
modal `InteractionScope`, exact focus history, and user navigation already
solve substantial dynamic continuation. The bounded missing layer is:

```text
one verified semantic operation
  -> event-driven fresh observation
  -> explicit bounded semantic condition
  -> exact authority and scope update
  -> rebuilt scene
  -> user continuation
```

Events wake observation; fresh GUI semantics establish truth. The deadline
bounds waiting and is never a success condition. Automatic execution of the
next task step is not part of this roadmap.

## 0.4A — Exact Authority and Bounded Transition Observation

Question: **Can a dynamic semantic operation reach a truthful bounded
post-state without treating the first event, a method return, or elapsed time
as success?**

Scope after explicit authorization:

- the smallest operation-adjacent transition observation behavior;
- explicit generic semantic postconditions and result classification;
- current session/generation, exact locator, and active-scope checks;
- events as coalesced wakeups plus fresh authoritative observation;
- deterministic stale, alternate, unchanged, ambiguous, cancelled, and
  deadline outcomes;
- separation of presentation continuity from mutation authority when a locator
  is replaced.

Exclusions: no new user-facing capability/key, workflow/task/transaction
engine, automatic next operation, Selection, menu framework, Expand command,
layout redesign, or release work.

Evidence: state-only menu, realization disclosure, modal creation/removal,
no-event fallback, unrelated event, stale/replaced target, and deadline. Use
GTK and Qt where already available.

Exit: generic dynamic action outcomes are established by fresh semantic
conditions; no first-event success or fuzzy replacement authority remains in
the qualified path; existing Text, Value, Choice, scope, and generation
invariants are retained.

## 0.4B — Dynamic Surface and Scope Continuation

Question: **Can the user safely enter, use, and leave a temporary semantic
surface through the existing scene and scope architecture?**

Scope after explicit authorization:

- bounded observation around already-supported named menu/dialog actions;
- enter a qualified Showing/modal/popup surface after refresh;
- rebuild and filter commands, choices, content, regions, and focus through the
  current active `InteractionScope`;
- invalidate a disappearing temporary surface and restore the prior exact
  focus anchor;
- honest handling of missing popup owner or unusable semantic surface.

Exclusions: no application/toolkit rules, new dialog subsystem, submenu
planner, menu compatibility campaign, Choice redesign, automatic item
selection, file-chooser implementation, or status framework.

Evidence: Qt state-realized menu, Qt modal, GTK created/destroyed dialog or file
chooser, and at least one ownerless-popup refusal.

Exit: three enter/leave surface shapes let the user continue manually in the
authoritative refreshed scene, while missing ownership or scope never exposes
blocked background operations as safe.

## 0.4C — Realization and Hierarchical Continuation

Question: **Can a structural transition expose current descendants for manual
use without claiming ownership or identity that Accessibility does not prove?**

Scope after explicit authorization:

- explicit state and realization postconditions;
- subtree refresh, stale old descendants, and new SceneBindings;
- manual navigation to currently realized descendants;
- honest ambiguity when realized siblings cannot be attributed to one trigger;
- partial/virtualized completeness preservation.

Exclusions: no automatic descendant search, fuzzy/name/geometry/index
reconciliation, Selection expansion, workflow planning, or ownership inference.
A production Expand capability is not authorized by this roadmap entry and
requires a separately reviewed atomic-capability decision.

Evidence: the GTK sibling-realization case plus a second independent
implementation if readily available; include locator replacement, ambiguous
ownership, collapse, and restoration.

Exit: user continuation works from a refreshed hierarchy; stale descendants
cannot retain authority; automation refuses when ownership is not public.

## 0.4D — Continuation UX and Theme Qualification

Question: **Can users understand transition progress and outcomes without a
workflow UI or automatic task runner?**

Scope after explicit authorization:

- concise presentation of observing, entered surface, cancelled, no usable
  surface, stale target, ambiguous transition, and deadline outcomes;
- representative cross-toolkit validation of state, surface/scope, and
  realization continuation;
- confirmation that the refreshed scene, existing navigation, and user choice
  are sufficient for the next step.

Exclusions: no layout redesign, workflow dashboard/history, task planner,
broad compatibility matrix, v0.5 primitive coverage, RC, or release work.

Evidence: user-controlled menu, modal, and hierarchical tasks with successful,
alternate, and refused outcomes.

Exit: at least three meaningfully different generic dynamic families provide
truthful manual continuation or deterministic refusal, and no task needs a
persistent workflow object merely to remember its prior GUI lifecycle.

## v0.4 completion boundary

v0.4 is complete when dynamic operation outcomes use bounded explicit semantic
conditions and authoritative reads; replacement cannot acquire operation
authority fuzzily; scope and bindings follow refreshed semantics; and users can
continue across representative state, realization, surface, scope,
replacement, and completion transitions. Widget count and automatic step count
are not exit criteria.

Selection, general Expand/menu/tree coverage, and complete file-chooser tasks
remain v0.5 concerns where their blocker is missing primitive or task
interaction. Long-running multi-application/window/restart robustness remains
v0.6. Deployment environments remain v0.7. No release phase or v0.8/v0.9 is
automatically created.

## Non-goals

Do not build a Workflow DSL/graph/engine, transition engine, compound operation
IR, transaction manager, AI planner, application recipe, event-correlation
registry, retry-by-guess, fixed-delay completion, input injection, coordinate
operation, anonymous action fallback, or fuzzy target matcher. Do not merge
resource External Modality with external complex-text mutation. The GUI remains
authoritative and the user remains in control.

## Recommended next decision

After architectural review, authorize only **0.4A — Exact Authority and
Bounded Transition Observation**. Completing Discovery does not authorize that
phase or any later phase.
