# GUI2TUI v0.5 Task & Interaction Completeness Discovery

Status: **COMPLETE**  
Primary conclusion: **A — TASK-COMPLETENESS MILESTONE JUSTIFIED**  
Starting source: `2c2ba487637a05bce1244099b75cf860764896ef`

Production changes during Discovery: **none**

This report asks which ordinary desktop tasks remain incomplete after the
qualified v0.1–v0.4 architecture. It is a task inventory, not an AT-SPI role
inventory and not authorization to implement the derived phases.

## 1. Method and evidence boundary

Discovery combined source inspection with bounded Linux AT-SPI experiments in
the established Ubuntu 24.04 arm64 guest under Xvfb. Temporary, uncommitted
GTK4, GTK3, and Qt6 fixtures used synthetic labels and a synthetic file tree
under `/tmp/gui2tui-v05-files`; they were removed after evidence collection.
The current pinned public APIs were read from `atspi 0.30.0` and
`atspi-proxies 0.14.0`. No private toolkit API, injected input, coordinates,
personal file content, production source change, or release work was used.

The prior [v0.3 capability Discovery](v0.3-capability-recovery.md) and the
[v0.4 milestone evidence](../validation/v0.4/milestone/HANDOFF.md) remain the
authority for already-qualified primitives and continuation. Existing v0.4
evidence was reused rather than rerunning its phase-close campaign.

## 2. What the current product can complete

Today GUI2TUI can complete these user tasks when the application exposes the
qualified public semantics:

- invoke a named Button or command action and observe a supported result;
- change a checkbox, toggle, or radio-style option through a compatible named
  action;
- edit a native single-line non-secret text field with authoritative readback;
- adjust a bounded Value and verify its resulting value;
- edit complete non-secret complex plain text through the configured external
  handler, with conflict detection and GUI readback;
- choose from a complete bounded `Choice`, including radio groups and choices
  whose options are already available without reproducing a GUI popup;
- read and navigate document-like content, headings, links, current table
  cells, and currently realized collection content;
- enter and leave modal task surfaces while background actions remain
  confined;
- reveal a qualified same-scope menu, manually invoke its current named item,
  and return to the ordinary scene;
- continue manually after state, surface, or structure changes using fresh
  current bindings;
- preserve graphical/external modality where terminal semantics are
  insufficient.

A bounded structured form containing a text field, checkbox, radio options,
complete Choice, Value, and Submit button therefore has no new primitive
blocker. A multi-page form can still be blocked by page-tab switching, and a
form requiring secret readback or an unsupported rich editor degrades safely.

## 3. Current capability pipeline

| Layer | Current writable behavior | Important boundary |
| --- | --- | --- |
| `SemanticCapability` | `SelectChildren`, `EditText`, `Value`, `EditComplexText` | There is no table-row, expansion, page-selection, or semantic-scroll capability. |
| `UiIntent` | `Activate`, `Toggle`, `Select`, `BeginChoice`, `OpenMenu`, `ClosePopup`, edit/value intents | No Expand, Collapse, page switch, multi-selection set operation, or collection reveal intent exists. |
| `SemanticOperation` | node action, toggle, list-item select, menu open/close, text writes, Value adjustment | `SelectNode` is list-oriented; table cells and tabs are not operation targets. |
| `BackendOperation` | named action, parent `SelectChild`, text writes, Value adjustment | No Table row/column operation and no selection readback contract. |
| `SceneBinding` | exact current locator, role, actions, capability, intent | Correct authority basis; it should be extended, not replaced. |
| Content models | Reader, current tables, current realized List/Tree/Table content | Navigation/readability exists without implying mutation or complete virtualization. |
| v0.4 continuation | bounded transition observation, scope/surface continuation, realization, fresh-scene rebinding | Already solves the lifecycle after a task operation; v0.5 must not rebuild it. |

The direct Choice path remains correct for a bounded complete option set.
Selection is needed for semantic collections, not as a replacement for Choice.

### Current Selection gap

The current list path can invoke a child action named `select`, `toggle`,
`activate`, or `click`, or call the parent's `Selection.SelectChild`. It then
refreshes and presents a success-oriented `Selected` status when the method
returned `true`; it does not independently require that a fresh selected-child
read identify the chosen current locator. This falls short of the v0.3
verified-capability standard and is the highest-priority v0.5 gap.

## 5. Structured-form evidence

The Qt6 fixture exposed an editable account field, checkbox, mutually
exclusive radio buttons, a complete three-option combo Choice, a bounded
slider, Submit, and an authoritative status label. Every control needed for
the representative task uses an already-qualified v0.3 capability or named
Action. v0.4 supplies modal/result continuation if the form is placed in a
dialog.

Conclusion: a bounded, fully exposed form is complete today. Tabs are a
separate page-navigation blocker, not evidence for a form engine. Password
content remains excluded, and no baseline claim requires secret readback.

## 6. Single-selection evidence and authority contract

### GTK4 Selection

A `Gtk.ListView` backed by `Gtk.SingleSelection` exposed a List with the
Selection interface and three exact current child objects. Initially the
selected-child read named Alpha. `SelectChild(1)` returned `true`; a fresh
`GetSelectedChild(0)` and `IsChildSelected(1)` identified the exact Beta child,
and the fresh tree moved Selected from Alpha to Beta.

### Qt6 item action

A single-select `QListWidget` did not expose Selection on its List container.
Each ListItem exposed exact `Toggle`; invoking Beta changed fresh Selected
state from Alpha to Beta. This is a second valid public shape, not a reason for
a toolkit branch.

### Required future authority

The minimum safe contract is:

```text
fresh current collection + exact current child/row locator
  -> derive the operation's current public index/action
  -> invoke within current generation and InteractionScope
  -> fresh selected-child/row or exact Selected-state readback
  -> confirm only when the intended current locator is selected
```

A cached integer index is not authority. Immediately before mutation, the
chosen locator must still be the child/row represented by that current index.
After mutation, fresh readback must identify the chosen locator. Reordering,
replacement, null/defunct selected references, and mere focus all refuse.

## 7. Multi-selection evidence

The controlled GTK MultiSelection List publicly reported Multiselectable.
Selection calls independently added Red and Blue, removed Red, selected all,
and cleared all; each step was reflected by fresh selected-child references.
The pinned interface also exposes `DeselectChild`, `DeselectSelectedChild`,
`ClearSelection`, and `SelectAll`.

Qt exposed Multiselectable on its items but no parent Selection interface.
Each item had `Toggle`: invoking Red once selected it and invoking the same
action again deselected it. The current product maps that action to the user
intent `Select`, demonstrating that a single-choice command cannot safely
stand in for add/remove membership.

Conclusion: multi-selection is technically plausible but is a separate,
higher-risk selected-set contract. No core baseline task found in this pass
requires select-all, arbitrary ordering, or broad multi-select. Keep it safe
unsupported/read-only until separately justified; do not widen the first
selection phase automatically.

## 8. Lists and tables

Lists expose two generic operation shapes: a parent's Selection interface or
an exact child action. Both need fresh target-specific readback.

The GTK3 chooser's Files Table exposed both Selection and Table, with three
rows and four columns. Selection reported all four cells of the selected row.
`Selection.SelectChild(8)` was rejected and did not select the second row;
`Table.AddRowSelection(1)` succeeded, `GetSelectedRows` changed from `[0]` to
`[1]`, and fresh selected children described the Beta row. Therefore Table row
selection is not safely reducible to generic direct-child selection.

The pinned Table API provides exact row/column counts, accessible-at
row/column, index-to-row/column mapping, selected rows/columns, per-cell
selection, and add/remove row/column selection. A future row operation can fit
the existing capability/intent/operation/backend pipeline, but it needs exact
current row evidence and row readback. Current table Reader/navigation remains
useful without mutation.

A Qt Table exposed current cells and item Toggle actions, but a diagnostic
Table metadata probe destabilized the temporary fixture. That is negative
implementation evidence, not a toolkit rule and not permission to guess.

## 9. Expand, Collapse, and hierarchy tasks

The existing GTK Demo evidence remains decisive. The `Constraints`
disclosure was Expandable/Expanded and advertised exact
`listitem.expand`, `listitem.collapse`, and `listitem.toggle-expand` actions.
Exact collapse/expand changed Expanded state, sibling rows disappeared or
reappeared, and v0.4 rebuilt the truthful current scene without inventing
ownership.

The controlled Qt Tree exposed an Expandable Workspace cell with only an
action named `Toggle`. Invoking it changed selection/recreated the row locator,
but did not establish Expanded state or reveal the child. Thus
Expandable + arbitrary Toggle is not a safe generic Expand rule. Advertised
Action strings are public evidence, not a standardized operation enum.

A future user-facing reveal intent is supportable only for an exact compatible
public action plus authoritative Expanded readback. Implementations lacking
that evidence must remain read-only. After confirmation, v0.4 already supplies
realization, stale-locator refusal, current hierarchy, focus recovery, and
manual descendant navigation.

Hierarchy task decomposition:

```text
reveal container                 missing bounded v0.5 capability
  -> verify Expanded             reuse v0.4 transition observation
  -> rebuild realized structure reuse v0.4 cache/scene
  -> navigate current content   existing navigation
  -> select/activate descendant selection or existing named Action
```

No TreeNavigator, descendant search, inferred ownership, or automatic path
opening is required.

## 10. Menus and context menus

The v0.4 Qt menu workflow already supplies the common task: exact ShowMenu,
fresh Showing items, manual Press, authoritative result, hiding, and stale
command removal in the same Window scope. A temporary nested menu added for
Discovery exposed `More commands` with exact ShowMenu and a hidden child with
Press. After the first and second fresh reveals, the nested item became
Showing and its exact Press was invokable. This uses the same existing menu
semantics and v0.4 continuation; it does not justify a menu framework.

The controlled Qt context target, despite having a graphical actions context
menu, exposed only Press and SetFocus. It exposed no semantic popup action and
the hidden context command was absent. Context-menu invocation is therefore
safe unsupported in this case. Right-click, Shift+F10, coordinates, or timing
would violate the project contract. Context menus are not a universal 1.0
requirement; when a target does expose a compatible public popup action, the
ordinary menu path may be used.

## 11. Tabs and page switching

GTK4 Notebook exposed a TabList with Selection. Selecting child 1 changed the
fresh selected child from General to Advanced and made the Advanced page
action current.

Qt6 exposed each PageTab with exact Press but no Selection interface or public
relation from tab to page. Pressing Advanced changed the TabList's public name
from General to Advanced, moved current focus, hid the General page action,
and showed the Advanced page action. Focus alone is not enough; the exact
TabList state/name and current page structure are stronger post-state
evidence that a future qualification must assess generically.

Tabs are common task navigation, not terminal RegionNavigator tabs. A bounded
page-switch operation can reuse the existing pipeline and v0.4 continuation,
but it needs cross-shape postconditions and must refuse implementations where
only focus changed.

## 12. File chooser task evidence

The synthetic GTK3 chooser confirms that surface lifecycle is no longer the
problem. Each chooser became the active modal `InteractionScope`, and exact
Cancel/confirmation returned to the host through v0.4's established model.

### Public task ingredients

- Location: a checked current breadcrumb button and ancestor breadcrumb
  buttons were public; the chooser also advertised exact `Show location`.
  This is usable current-location evidence in this implementation, not a
  universal filesystem-path contract.
- Listing: Files was a PartialRealized Table with public Table/Selection
  interfaces, current row names, columns, and selected-row state.
- Type: text files exposed a type such as `Empty document`; the directory row
  had no explicit accessible file/folder type and its image had no meaningful
  public name. GUI2TUI must not infer type from icon, suffix, or geometry.
- Selection: Table row selection worked through `AddRowSelection`, while
  `Selection.SelectChild` was rejected.
- Traversal: exact advertised `Activate` on the folder-name cell changed the
  checked breadcrumb and refreshed the listing to `nested.txt`.
- Open: with a synthetic selected file, exact Open dismissed the chooser and
  the host exposed its accepted result.
- Choose Folder: exact confirmation of the currently checked synthetic folder
  dismissed the chooser and exposed the accepted result. The accessible
  confirmation label was `Open`, so role/window-title guesses must not rename
  its semantics.
- Save As: a visible editable filename contained `new-document.txt`, current
  breadcrumbs were present, exact Save completed the harmless host flow, and
  no file was created by the validation host. Existing-file overwrite and
  authoritative final target semantics were deliberately not exercised.
- Virtualization: the listing was PartialRealized; no whole-directory claim is
  available.

### 1.0 chooser decision

**B — Open + Choose Folder are baseline; Save As needs further evidence.**

Open and Choose Folder have high task value and can be constructed from
bounded collection/table targeting, exact actions, current breadcrumbs, and
v0.4 continuation. They must remain conditional on public current semantics;
missing file/directory type is shown honestly rather than guessed. Save As has
most ingredients but overwrite chains and authoritative destination
confirmation carry materially different safety requirements. It should not be
forced into the initial baseline merely for symmetry.

## 13. Virtualization and semantic scrolling

The pinned Component API exposes `ScrollTo(ScrollType)` and
`ScrollToPoint`. `ScrollTo` can be semantic for a **known exact accessible
object**; `ScrollToPoint` remains coordinate-oriented and is not an acceptable
fallback for task semantics.

The controlled GTK ListView had 200 model items but exposed only five current
accessible children. Current GUI2TUI reconstructed those five as a Complete
Choice because the accessibility surface did not report `ManagesDescendants`
or a logical total. Calling `SelectChild(100)` returned `true`, yet fresh
selected-child readback was the AT-SPI null object while
`IsChildSelected(100)` returned true. This proves all of the following:

- method acceptance is not selection truth;
- a model/logical index is not necessarily a current accessible-child index;
- an unknown offscreen item has no exact locator to authorize `ScrollTo`;
- current completeness can be unknowable even when the toolkit has more data.

The first selection phase must prevent accepted-but-unverifiable selection and
must not advertise the realized window as a known complete logical choice when
completeness cannot be established. Discovery does not yet justify a generic
“advance collection” operation: AT-SPI exposes object scroll-to, not an exact
next-unrealized-item target. Exhaustive traversal of virtual collections is
deferred; current realized content remains useful and honest.

## 14. Task dependency analysis

```text
Single list choice
└─ exact current selection + authoritative selected-target readback (missing)

Table task
├─ current cell navigation/readability (existing)
└─ exact row selection + selected-row readback (missing)

Hierarchy task
├─ exact semantic reveal/hide intent (missing where qualifiable)
├─ bounded transition and realization (v0.4)
├─ current navigation (existing)
└─ descendant selection or named activation (selection gap or existing)

Page-tab task
├─ Selection or exact tab Action (public implementation shape)
├─ authoritative current-page post-state (missing qualification)
└─ current content continuation (v0.4)

File Open / Choose Folder
├─ modal scope and return (v0.4)
├─ current location/listing (public, sometimes incomplete)
├─ exact table/list selection (missing)
├─ directory activation (not surfaced)
├─ exact confirmation Action (existing)
└─ completion continuation (v0.4)
```

No dependency requires a persistent `TaskSession`, workflow engine,
collection manager, or task planner. The current scene plus v0.4 continuation
remains sufficient between user-controlled steps.

## 15. False gaps and already-solved areas

These apparent feature gaps do **not** justify new infrastructure:

- A Choice whose complete options are already semantic does not need its
  graphical popup reproduced.
- Modal entry/exit and dialog confinement do not need a Dialog subsystem.
- Temporary and nested named menu items do not require a Menu framework.
- Realization after Expand does not need an ownership graph or automatic
  descendant association.
- Ordinary current-scene navigation is sufficient after hierarchy changes; a
  TreeNavigator is unnecessary.
- Table readability/navigation exists independently of table selection.
- Buttons, hyperlinks with compatible named actions, toggles, radio choices,
  Text, Value, and qualified complex text do not need duplicate capability
  families.
- File chooser surface lifecycle is v0.4 work already completed; only its task
  primitives remain.

## 16. Negative and limitation evidence

1. **Virtual selection acceptance without an exact result.** GTK accepted
   logical index 100 while only five accessible children existed and returned
   a null selected object. GUI2TUI must reject/unconfirm it; it must not trust
   acceptance, index, or focus.
2. **Table Selection is not child Selection.** GTK chooser
   `Selection.SelectChild` rejected a visible row index while
   `Table.AddRowSelection` succeeded and produced exact row readback. GUI2TUI
   must not guess a flattened cell index.
3. **Expand action ambiguity.** GTK exposed explicit expand/collapse action
   names and Expanded readback; the Qt Tree's Toggle only changed selection
   and did not reveal the child. GUI2TUI must not map arbitrary Toggle to
   Expand based on role or Expandable alone.
4. **No context-menu trigger.** A graphical Qt context menu had no public
   semantic opener on its target. Safe behavior is no context-menu affordance.
5. **Chooser type incompleteness.** The synthetic directory row lacked a
   reliable public directory type. GUI2TUI must not use icon, filename suffix,
   or layout to invent it.

## 17. Proposed GUI2TUI 1.0 common-task baseline

The bounded baseline should require the following **when sufficient public
Accessibility semantics exist**:

1. Complete a common structured form using qualified text, bounded Choice,
   checkbox/toggle/radio, Value, Submit, and observable result.
2. Invoke ordinary Buttons, hyperlinks, and standard/nested menu commands via
   exact compatible named actions.
3. Select one exact current item or table row with authoritative target
   readback and safe refusal under reorder, replacement, or virtualization.
4. Switch an accessible page tab and continue from the fresh current page.
5. Reveal or hide hierarchy content only through a qualified public semantic
   action and Expanded readback, then navigate manually through current public
   structure.
6. Complete common modal confirmation/settings tasks whose contained controls
   are otherwise qualified.
7. Open a synthetic/non-secret file and choose the current or reachable folder
   through exact current collection/location semantics, with v0.4 scope and
   completion observation.
8. Read and navigate current list/table/Reader content while representing
   partial or virtualized coverage honestly.

The baseline permits `COMPLETE`, `READ-ONLY`, `EXTERNAL MODALITY`, or
`SAFE UNSUPPORTED` when the required public semantics are absent. It does not
claim universal application, toolkit, widget, file chooser, or hierarchy
compatibility.

## 18. Explicit deferred and non-required tasks

### Useful but optional / post-baseline

- arbitrary multi-selection, select-all, ordered selection sets;
- Save As overwrite confirmation and broad destination handling;
- exhaustive traversal/search of virtualized collections;
- broad table column selection and table-editing semantics;
- menu search and unusual submenu structures.

### Not required for 1.0

- pointer-only context menus without a public semantic opener;
- arbitrary drag and drop;
- hover-only tooltips as an interaction family;
- pixel scroll, mouse-wheel, coordinate, or keyboard-emulated tasks;
- universal tree, table, chooser, editor, or application completeness.

### Accessibility-limited or external modality

- tasks lacking an exact target, public operation, current scope, or
  authoritative readback;
- visual-only file/directory or hierarchy distinctions;
- graphical/media tasks whose useful modality should remain external;
- secret-content readback and unqualified rich/partial text mutation.

## 19. Capability leverage and risk

| Candidate capability | Important tasks unlocked | Risk | Scope |
| --- | --- | --- | --- |
| Verified exact single collection selection | Lists, table rows, tabs in Selection implementations, file/folder chooser | Stale/reordered index, null selected object, Table-vs-Selection semantics | **MEDIUM** |
| Table row selection | Data-task rows, chooser files/folders | Row/cell identity, virtualization, implementation instability | **MEDIUM** |
| Qualified Expand/Collapse | Tree/disclosure tasks | Action-name ambiguity and state-only vs realization distinction | **MEDIUM** |
| Qualified page switching | Multi-page forms/settings | Selection vs named Action shapes; post-state evidence | **MEDIUM** |
| File/folder chooser task composition | High-value Open and Choose Folder tasks | Location/type incompleteness, traversal, task completion | **LARGE** |
| Multi-selection set operations | Tag/file/bulk tasks | Non-idempotent Toggle, exact set readback, reorder/virtualization | **LARGE** |
| Scroll known object into view | Some current-object reachability | Cannot target an unrealized unknown item; no collection-advance contract | **SMALL alone / insufficient for exhaustive virtualization** |

Highest leverage is verified exact single selection, including Table row
semantics. It unlocks list/table tasks and is a prerequisite for chooser work.
Expand and page switching then unlock distinct common navigation tasks while
reusing v0.4. File/folder choice should integrate those primitives rather than
introduce a chooser subsystem.

## 20. Architecture and roadmap conclusion

**A — TASK-COMPLETENESS MILESTONE JUSTIFIED.**

Several high-value ordinary tasks are blocked by a bounded set of missing or
incompletely qualified semantic operations: verified current selection,
Table-row selection, safe hierarchy reveal, and page switching. File/folder
choice composes those operations with already-qualified v0.4 continuation.
No distinct missing architectural layer, task session, workflow engine, or
application adapter was found.

The current `SemanticCapability` → `UiIntent` → `SemanticOperation` →
`BackendOperation` path remains the right extension point. v0.4 remains the
authoritative transition/scope/realization layer. v0.6 still owns long-running
sessions, reconnect, event backpressure, restarts, and resource health. v0.7
still owns deployment environments, permissions, installation, and support
contracts. The pre-1.0 internal milestone/release policy is unchanged.

## 21. Recommended bounded phases

The derived [v0.5 roadmap](v0.5-roadmap.md) proposes four phases:

1. **0.5A — Verified Current Collection Selection**
2. **0.5B — Hierarchy Reveal and Page Continuation**
3. **0.5C — File and Folder Choice Tasks**
4. **0.5D — Common Task Baseline Qualification**

The dependency order is intentional: chooser work depends on exact current
selection; reveal/page operations depend on v0.4 but not on a new task engine;
integration comes last. No phase is automatically authorized.

## 22. Proposed v0.5 exit definition

v0.5 is complete when the agreed common-task baseline can be completed or
degraded honestly through generic public semantics:

- common structured forms and supported dialogs complete without a form or
  dialog framework;
- one exact current list item or Table row can be selected with authoritative
  readback and stale/reordered/virtualized ambiguity refuses;
- qualified page tabs and hierarchy reveal operations lead through v0.4 to a
  fresh current scene for manual continuation;
- generic Open-file and Choose-folder tasks complete on evidence-backed
  accessible choosers, while type/location uncertainty remains explicit;
- ordinary named commands/menus and current read/navigation capabilities do
  not regress;
- false completeness, false selection success, anonymous actions, inferred
  hierarchy, input injection, coordinates, and app/toolkit branches remain
  absent;
- P0 = 0, P1 = 0, relevant Linux live evidence passes, representative prior
  layers regress cleanly, and milestone-close source/docs quality passes.

Success is measured by tasks and safe degradation, never role/widget/app/test
counts. Multi-select breadth, Save As overwrite, exhaustive virtualization,
pointer-only context menus, runtime continuity, deployment, RC, and release
remain outside this exit definition unless later user review changes it.
