# GUI2TUI v1.0 Integration & Stabilization Roadmap

This roadmap follows the completed [v1.0 Integration
Discovery](v1.0-integration-discovery.md). It is a recommendation only.
Implementation, RC creation, package-version changes, tags, publication and
release remain separately authorized actions.

## 1. Recommended route

```text
v0.7 milestone-qualified baseline
  -> 1.0A Final-source product contract and end-to-end baseline
  -> 1.0B Cross-milestone task integration
  -> 1.0C Terminal usability and recovery
  -> 1.0D Stability, performance and environment qualification
  -> 1.0E Product contract freeze and release qualification
  -> separately authorized v1.0.0 RC
  -> separately authorized public v1.0.0 release
```

The phases are ordered by evidence dependency, not by historical milestone
shape. A phase may make a minimal generic fix when a concrete defect is found;
it must not turn a qualification phase into a feature expansion.

## 2. Phase 1.0A — Final-source product contract and end-to-end baseline

### Actual problem

The current source has a coherent user flow, but the final 1.0 support
contract is not frozen and the installed-package evidence is only a
representative subset of the v0.5 task baseline. A release decision cannot
rest on combining historical phase PASS records by implication.

### Existing evidence

- v0.4-v0.7 are internally milestone-qualified.
- v0.7E proved exact-source installation, Doctor, Managed lifecycle, package
  helper resolution, and representative semantic operation on the recorded
  package/environment topologies.
- Current source quality checks pass; the full v0.5 task baseline remains
  historical evidence rather than a new installed-package run.

### Authorized scope

- Select the candidate 1.0 Supported/Limited/Optional/Not Tested/Deferred
  rows from the v0.7 matrix.
- Build a small evidence manifest that names exact source, package, fixture,
  topology, task, result, and cleanup.
- Run the first installed-package end-to-end path from documented installation
  through application selection and one representative task.
- Correct documentation inconsistencies such as the x86_64 qualification
  wording.
- Fix only concrete generic integration defects that prevent this path.

### Reuse

Existing installer, Doctor, Managed helper, selector, launcher, semantic
authority, current-scene continuation, v0.5 fixtures, v0.6 lifecycle harnesses,
v0.7 package harnesses, and documentation audit.

### Explicit non-goals

No new widget family, application adapter, toolkit API, workflow engine,
Remote Companion, native VT claim by analogy, package publication, version
bump, RC, or broad performance campaign.

### Linux live evidence

At least one exact installed aarch64 package run on the existing qualified
Managed topology must show: install, Doctor, session selection, application
selection, a task, authoritative result, safe exit, stop/uninstall. If another
architecture or topology is intended for the 1.0 Supported matrix, it needs
its own attributable evidence.

### Regression and exit conditions

- Product contract rows are explicit and no row is broader than its evidence.
- One documented end-to-end task completes through user-selected semantic
  operations and authoritative readback.
- No P0/P1; no authority migration, false success, password exposure, or
  private API/input injection.
- Docs audit, `git diff --check`, Rust quality, and relevant fixture checks pass.
- Phase 1.0B receives a source/package/evidence manifest, not an assumption.

## 3. Phase 1.0B — Cross-milestone task integration

### Actual problem

The promised common-task baseline must survive as one product path, including
dynamic changes and partial content, rather than only as separately qualified
phase evidence.

### Existing evidence

v0.5D passed structured forms, collection/table selection, menus/dialogs,
PageTab, hierarchy, Open File, Choose Folder, Reader and safe negative
boundaries. v0.4 and v0.6 supply continuation and lifecycle contracts.

### Authorized scope

Run a targeted matrix from the installed package and current source covering:

- structured form with Choice, Toggle, Value, PageTab and result;
- modal dialog/menu scope and manual return;
- exact collection/table selection and row readback;
- hierarchy reveal with explicit Expand/readback and safe Toggle refusal;
- Open File and Choose Folder through partial realized tables;
- Reader/search with partial content and one dynamic refresh;
- one external-text success/conflict/recovery path; and
- one stale/unsupported/security negative path.

Fix only generic failures that are reproduced in these tasks. Preserve the
existing current-scene/manual-continuation model.

### Explicit non-goals

No multi-selection expansion, Save As overwrite, exhaustive virtualization,
drag/drop, rich-text fidelity, pointer-only context menus, task runtime, or
application-specific workaround.

### Linux live evidence and regression

Use the existing GTK/Qt/browser/chooser fixtures where they carry generic
semantic evidence. At least one installed aarch64 Managed run must cover the
core task path; historical phase evidence may be cited for a task only after a
source-identity audit shows no relevant production change. Re-run directly
affected Rust tests and the full source-quality matrix only at the phase gate.

### Measurable exit conditions

- Every v0.5 1.0 baseline row is either PASS on the final package or has an
  explicit safe limitation with a user-visible refusal and no false claim.
- At least one Open File and one Choose Folder task prove the final
  application-visible result, not merely backend acceptance.
- Dynamic task changes rebuild current scope/scene and reject all frozen old
  commands.
- Spatial and flat presentation preserve the same semantic operations.
- P0 = 0, open P1 = 0, and no new unbounded or unsafe behavior.

## 4. Phase 1.0C — Terminal usability and recovery

### Actual problem

A semantically correct runtime can still fail a terminal-only user through
clipping, undiscoverable controls, confusing status language, or an unclear
recovery path. Current unit tests and historical frames do not substitute for
final-source terminal observation.

### Authorized scope

- Observe selector, initial scene, region navigation, Tab focus, Command
  Palette, Reader, Choice, Table, partial content, help and diagnostics.
- Use a small declared terminal-size set, including one narrow size, one
  normal size and one resized PTY.
- Exercise modal entry/exit, application switch/restart, event overflow
  resync, stale command refusal, external-handler handoff, resize,
  SIGTSTP/SIGCONT where available, and the documented SSH disconnect boundary.
- Adjust only presentation/status/help wording or generic focus/recovery logic
  required by a reproduced usability defect.

### Explicit non-goals

No screenshot-derived semantics, pixel layout, mouse/keyboard injection into
the GUI, new terminal manager, new TTY attachment, or automatic task recovery.

### Linux live evidence and regression

Use real PTY/SSH input and text-frame capture for the TUI; use the GUI only as
the authoritative application state. Preserve the existing v0.6 terminal and
handler ownership evidence and v0.7 SSH evidence.

### Measurable exit conditions

- Every declared core task is reachable using documented keys at the normal
  terminal size and remains navigable at the declared narrow size.
- Help text matches actual dispatch for Scene, Reader, Choice, Table, Command,
  Edit, Modality and unavailable/recovery contexts.
- A stale/timeout/conflict/unsupported result states the outcome and one
  executable next step; no internal runtime taxonomy is required of the user.
- No duplicate terminal reader or unrecovered raw/alternate-screen state is
  observed on supported exit paths.
- Resize, suspend/resume, handler return, and fresh application selection do
  not revive old operation authority.

## 5. Phase 1.0D — Stability, performance and environment qualification

### Actual problem

v0.6 proves bounded ownership in a controlled mixed lifecycle, but 1.0 needs
release-facing measurements and a final decision about each environment row.

### Authorized scope

- Establish measurements for first usable selector/scene, complete and
  incomplete 5k-node bootstrap, p50/p95 operation/readback, event-overflow
  resync, resize redraw, and external-handler return.
- Run one bounded multi-step soak (for example 30 minutes or 100 semantic
  operations, whichever is reached first) on a declared topology.
- Track FDs, threads, child processes/zombies, event queue/tickets, cache/view
  bounds, private artifacts, and terminal reader ownership.
- Qualify native x86_64 hardware if x86_64 is to be a full Supported row;
  otherwise label it package/ABI/emulation-limited. Qualify real Linux VT if
  local VT is to be Supported; do not substitute a PTY.
- Reconfirm each Wayland/SSH/Docker row only within its recorded boundaries.

### Explicit non-goals

No large benchmark campaign, general performance optimization, broader distro
matrix, bundled compositor, production OCI image, VNC/RDP, Remote Companion,
or application compatibility sweep.

### Proposed measurable gates

These are candidate 1.0 gates to be baselined and frozen at the phase start;
they are not current PASS claims:

- every bounded operation either completes or reports a truthful result within
  the configured default backend deadline (5 seconds), with no indefinite
  wait;
- Doctor and no-backend recovery remain bounded and actionable, with no raw
  credentials or bus addresses in output;
- complete and incomplete 5k-node bootstrap results are reported separately,
  with no incomplete tree presented as complete;
- after the bounded soak settles, no unexplained growth in FDs, threads,
  children/zombies, queue/ticket counts, cache/view residency, or artifact
  ownership occurs; and
- any threshold exception is tied to a named application/topology and becomes
  a documented limit rather than a silent global claim.

### Exit conditions

- Stability/resource report passes for each declared core topology.
- Environment matrix is frozen with evidence and limitations.
- No P0/P1, no false success, no leaked password/private artifact payload,
  and no unbounded task or child ownership.

## 6. Phase 1.0E — Product contract freeze and release qualification

### Actual problem

The current repository has reusable release scripts and historical public
release evidence, but no v1.0 package, public support contract, RC, or final
source qualification exists.

### Authorized scope

- Freeze README, Getting Started, Deployment, Compatibility, Limitations,
  Troubleshooting, Doctor wording, package architecture/ABI floors, and
  support matrix against the actual evidence.
- Build exact candidate packages using the existing release pipeline.
- Run source quality, installer/uninstaller, checksum/manifest/ABI,
  extracted-package and declared-environment qualification from the exact
  candidate source.
- Prepare release notes, provenance/attestation inputs, migration/upgrade
  notes, and a rollback/stop procedure.

### Explicit non-goals

No public publication, tag movement, package-version change, GitHub Release,
or RC creation without a separate explicit authorization. RC qualification is
the next authorization boundary after this phase, not part of Discovery.

### Exit conditions

- All 1.0 acceptance criteria below pass on exact candidate source.
- P0 = 0 and P1 = 0; all remaining P2/limitations are documented and
  non-blocking.
- Every support row is either evidenced or explicitly excluded.
- Release bytes, docs, checksums, provenance and uninstall behavior agree.
- User separately authorizes the v1.0.0 RC.

## 7. Proposed v1.0 product acceptance contract

A v1.0 candidate is acceptable only when all of the following are true:

### Installation and environment

- A user can follow the published Linux instructions from a terminal, install
  the exact package without root, and run it outside the checkout.
- Required helpers resolve from the installed layout; safe uninstall removes
  only owned files and preserves user configuration/runtime/recovery data.
- For every declared Supported environment, the package can select the correct
  session, create/reuse/stop the required Managed environment where promised,
  and explain missing system dependencies without pretending to install them.
- The support matrix explicitly names the recorded architecture, distribution,
  display/compositor, terminal topology and known limits.

### First-use and task completion

- A terminal-only user can obtain a fresh application enumeration, choose an
  exact current application or a verified direct-argv launcher, see a usable
  initial scene, and follow contextual help to a safe operation.
- The final package completes the declared v0.5 common-task baseline where
  public semantics qualify it: structured form, common dialog/menu, exact
  selection/table row, PageTab, qualified hierarchy, Open File, Choose Folder,
  Reader/current collection, and qualified complete plain-text external edit.
- The GUI's authoritative result/readback, not invocation return, event timing,
  local optimistic state, filesystem state, or descriptive identity, proves
  success.
- Partial, unsupported, secret, stale, ambiguous, unavailable and external
  modality cases are visibly honest and give a safe next action where one
  exists.

### Dynamic and runtime safety

- Modal scopes, popup/realization changes, application replacement, transport
  recovery, event overflow, terminal suspend/resume, handler handoff and
  declared disconnect boundaries preserve exact authority and current-scene
  manual continuation.
- No old generation, locator, ticket, command, candidate, or focus binding can
  operate or confirm a replacement target.
- Password content never enters cache, renderer, logs, reports or handlers;
  private candidates/artifacts retain ownership and bounded cleanup.
- Supported normal exits restore terminal state, and a destroyed PTY is
  documented as requiring fresh reconnection rather than claimed as silently
  recoverable.

### Quality and performance

- Current source and exact candidate packages pass the relevant Rust,
  documentation, installer, package, and declared Linux live gates.
- Every bounded operation has a deadline or explicit cancellation and produces
  a truthful user-visible result.
- The frozen performance/stability thresholds from Phase 1.0D pass, with
  application/topology-specific exceptions documented rather than generalized.
- No P0 or P1 remains open. P2 items are either fixed or explicitly accepted
  as safe, non-blocking limitations.

## 8. Authorization boundaries

| Work | Status after Discovery |
| --- | --- |
| Discovery documents and roadmap | Completed by this task only |
| 1.0A-1.0E implementation/qualification | Not authorized by this task |
| New semantic interaction families | Not authorized |
| Remote Companion/cross-host protocol | Deferred beyond 1.0 |
| Package version change | Not authorized |
| v1.0.0 RC/tag/release | Not authorized |
| Public publication/deployment | Not authorized |

## 9. Recommended next authorization

Authorize **Phase 1.0A — Final-source product contract and end-to-end
baseline**. Its first deliverable should be a frozen candidate support matrix
and an installed-package evidence manifest, followed by the smallest
end-to-end common-task qualification needed to decide whether G1/G2 are
evidence gaps or concrete generic defects.

Do not authorize broad feature development before that decision.
