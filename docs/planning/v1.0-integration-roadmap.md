# GUI2TUI v1.0 Integration & Stabilization Roadmap

This roadmap follows the completed [v1.0 Integration
Discovery](v1.0-integration-discovery.md). Phase 1.0C and internal
`1.0.0-rc.1` preparation are validated. The final `1.0.0` source preparation
is now authorized; publication remains gated by the final release checks.

## 1. Recommended route

```text
v0.7 milestone-qualified baseline
  -> 1.0A Product integration and task completeness
  -> 1.0B Usability, reliability and stabilization
  -> 1.0C Final qualification and release readiness
  -> internal v1.0.0-rc.1 preparation — QUALIFIED
  -> v1.0.0 final source and package qualification — IN PROGRESS
  -> public v1.0.0 publication — gated by final checks
```

The phases are ordered by evidence dependency, not by historical milestone
shape. A phase may make a minimal generic fix when a concrete defect is found;
it must not turn a qualification phase into a feature expansion.

## 2. Phase 1.0A — Product integration and task completeness

### Close status

**VALIDATED** on the final-source aarch64 user-prefix package in the
qualified Managed Xvfb/Docker PTY topology. Open File and Choose Folder were
completed through the installed TUI with fresh caller readback. The Qt
ComboBox shape was isolated as a safe public-Accessibility limitation: its
transient ListItems advertise `Toggle` but do not expose a reliable
target-specific selected/current result after the attempted operation. The
TUI refused to claim success. This does not invalidate the baseline because
the qualified GTK selection shape supplies the supported structured-choice
evidence; the Qt shape is an explicit unsupported-by-public-semantics row.

1.0B was subsequently authorized and has completed its bounded usability,
reliability, environment and formal soak evidence. See the
[1.0B HANDOFF](../validation/v1.0/1.0b-usability-reliability-stabilization/HANDOFF.md).
The result is **VALIDATED** with the evidence boundaries recorded there.
1.0C was subsequently authorized and is now **VALIDATED**. Its final support
matrix, exact candidate package identity and release-readiness evidence are
recorded in the [1.0C HANDOFF](../validation/v1.0/1.0c-final-qualification-release-readiness/HANDOFF.md).

### Actual problem

The current source has a coherent user flow, but the final 1.0 support
contract and the installed-package evidence are not yet confirmed as one
product path. A release decision cannot rest on combining historical phase
PASS records by implication. The real question for this phase is whether a
terminal-only user can install the current package, establish a Headless-first
session, select an application, operate the TUI, complete the v0.5
Common-task Baseline, observe an authoritative result, and exit safely.

### Existing evidence

- v0.4-v0.7 are internally milestone-qualified.
- v0.7E proved exact-source installation, Doctor, Managed lifecycle, package
  helper resolution, and representative semantic operation on the recorded
  package/environment topologies.
- v0.5D passed the Common-task Baseline as milestone evidence, including
  forms, collection/table selection, menus/dialogs, PageTab, hierarchy,
  Open File, Choose Folder, Reader and safe negative boundaries.
- Current source quality checks pass; the complete baseline remains historical
  evidence rather than a new installed-package run.

### Authorized scope

- Select the candidate 1.0 Supported/Limited/Optional/Not Tested/Deferred
  rows from the v0.7 matrix and record them in an evidence manifest.
- Build an independent package from the current source and run the complete
  documented first-use path: installation, Headless environment, application
  launch/selection, TUI operation, authoritative result, safe exit and
  cleanup.
- Exercise the v0.5 Common-task Baseline through the installed TUI, covering
  structured forms, Selection, Table row, PageTab, qualified hierarchy,
  menus, dialogs, Open File, Choose Folder, Reader, Value, qualified text
  editing, and dynamic manual continuation.
- Use Inspector and test interfaces only for evidence and diagnosis; they do
  not substitute for user operations in the product TUI.
- Correct documentation inconsistencies such as the x86_64 qualification
  wording and fix only concrete generic integration defects reproduced by
  these tasks.

### Reuse

Existing installer, Doctor, Managed helper, selector, launcher, semantic
authority, current-scene continuation, v0.5 fixtures, v0.6 lifecycle harnesses,
v0.7 package harnesses, and documentation audit.

### Explicit non-goals

No new widget family, application adapter, toolkit API, workflow engine,
Remote Companion, native VT claim by analogy, package publication, version
bump, RC, or broad performance campaign.

### Linux live evidence

At least one exact installed package run on the existing qualified Managed
topology must show the complete first-use chain and the Common-task Baseline.
The run must use the actual installed TUI for each user operation and must
name architecture, distribution, display/session, terminal topology, source,
package, fixture, result and cleanup. If another architecture or topology is
intended for the 1.0 Supported matrix, it needs its own attributable evidence.

### Regression and exit conditions

- Product contract rows are explicit and no row is broader than its evidence.
- Every v0.5 baseline row is either PASS on the final package or has an
  explicit safe limitation with a user-visible refusal and no false claim.
- The documented end-to-end chain completes through user-selected semantic
  operations and authoritative readback, including at least one file chooser
  result and one dynamic manual continuation.
- No P0/P1; no authority migration, false success, password exposure, or
  private API/input injection.
- Docs audit, `git diff --check`, Rust quality, and relevant fixture checks pass.
- Phase 1.0B receives a source/package/evidence manifest and task-result
  record, not an assumption.

## 3. Phase 1.0B — Usability, reliability and stabilization

### Actual problem

The integrated task path must remain usable and truthful in a terminal over
time. Correct semantics alone are insufficient if clipping, undiscoverable
controls, confusing status language, terminal ownership failures, resource
growth, or an unqualified environment prevents a terminal-only user from
continuing safely.

### Existing evidence

1.0A supplies the final-source task manifest and baseline results. v0.4 and
v0.6 supply continuation, authority, terminal ownership and lifecycle
contracts. v0.7 supplies the bounded Headless-first environment evidence.

### Authorized scope

- Observe selector, initial scene, region navigation, Tab focus, Command
  Palette, Reader, Choice, Table, partial content, help and diagnostics at
  declared terminal sizes, including a narrow size and a resized PTY.
- Exercise modal entry/exit, application switch/restart, event-overflow
  resync, stale command refusal, external-handler handoff, resize,
  SIGTSTP/SIGCONT where available, and the documented SSH disconnect boundary.
- Establish bounded measurements for first usable selector/scene, complete and
  incomplete 5k-node bootstrap, p50/p95 operation/readback, event-overflow
  resync, resize redraw, and external-handler return.
- Run one bounded multi-step soak (for example 30 minutes or 100 semantic
  operations, whichever is reached first) on a declared topology. Track file
  descriptors, threads, children/zombies, event queues/tickets, cache/view
  bounds, private artifacts, and terminal reader ownership.
- Qualify native x86_64 hardware if x86_64 is to be a full Supported row;
  otherwise label it package/ABI/emulation-limited. Qualify real Linux VT if
  local VT is to be Supported; do not substitute a PTY. Reconfirm each
  Wayland/SSH/Docker row only within its recorded boundaries.
- Fix only generic presentation, status, focus, recovery, lifecycle or
  resource defects reproduced in these observations. Preserve the existing
  current-scene/manual-continuation model.

### Explicit non-goals

No new semantic interaction family, multi-selection expansion, Save As
overwrite, exhaustive virtualization, drag/drop, rich-text fidelity,
pointer-only context menus, task runtime, application-specific workaround,
large benchmark campaign, general performance optimization, broader distro
matrix, bundled compositor, production OCI image, VNC/RDP, Remote Companion,
or application compatibility sweep.

### Linux live evidence and regression

Use the existing GTK/Qt/browser/chooser fixtures where they carry generic
semantic evidence. Use real PTY/SSH input and text-frame capture for the TUI;
use the GUI only as the authoritative application state. At least one
installed package Managed run must cover the integrated task path. Historical
phase evidence may be cited only after a source-identity audit shows no
relevant production change. Re-run directly affected Rust tests and the full
source-quality matrix at the phase gate.

### Proposed measurable gates

These are candidate 1.0 gates to be baselined and frozen at the phase start;
they are not current PASS claims:

- every bounded operation either completes or reports a truthful result within
  the configured default backend deadline (5 seconds), with no indefinite
  wait;
- Doctor and no-backend recovery remain bounded and actionable, with no raw
  credentials or bus addresses in output;
- complete and incomplete 5k-node bootstrap results are reported separately,
  with no incomplete tree presented as complete;
- after the bounded soak settles, no unexplained growth in FDs, threads,
  children/zombies, queue/ticket counts, cache/view residency, or artifact
  ownership occurs; and
- any threshold exception is tied to a named application/topology and becomes
  a documented limit rather than a silent global claim.

### Exit conditions

- Stability/resource report passes for each declared core topology.
- Environment matrix is frozen with evidence and limitations.
- No P0/P1, no false success, no leaked password/private artifact payload,
  and no unbounded task or child ownership.

### Close status

**VALIDATED**. No production Rust fix was required. The formal requalification
soak passed after the validation-only fresh-prompt cleanup fix.

## 5. Proposed v1.0 product acceptance contract

A v1.0 candidate is acceptable only when all of the following are true:

### Installation and environment

- A user can follow the published Linux instructions from a terminal, install
  the exact package without root, and run it outside the checkout.
- Required helpers resolve from the installed layout; safe uninstall removes
  only owned files and preserves user configuration/runtime/recovery data.
- For every declared Supported environment, the package can select the correct
  session, create/reuse/stop the required Managed environment where promised,
  and explain missing system dependencies without pretending to install them.
- The support matrix explicitly names the recorded architecture, distribution,
  display/compositor, terminal topology and known limits.

### First-use and task completion

- A terminal-only user can obtain a fresh application enumeration, choose an
  exact current application or a verified direct-argv launcher, see a usable
  initial scene, and follow contextual help to a safe operation.
- The final package completes the declared v0.5 common-task baseline where
  public semantics qualify it: structured form, common dialog/menu, exact
  selection/table row, PageTab, qualified hierarchy, Open File, Choose Folder,
  Reader/current collection, and qualified complete plain-text external edit.
- The GUI's authoritative result/readback, not invocation return, event timing,
  local optimistic state, filesystem state, or descriptive identity, proves
  success.
- Partial, unsupported, secret, stale, ambiguous, unavailable and external
  modality cases are visibly honest and give a safe next action where one
  exists.

### Dynamic and runtime safety

- Modal scopes, popup/realization changes, application replacement, transport
  recovery, event overflow, terminal suspend/resume, handler handoff and
  declared disconnect boundaries preserve exact authority and current-scene
  manual continuation.
- No old generation, locator, ticket, command, candidate, or focus binding can
  operate or confirm a replacement target.
- Password content never enters cache, renderer, logs, reports or handlers;
  private candidates/artifacts retain ownership and bounded cleanup.
- Supported normal exits restore terminal state, and a destroyed PTY is
  documented as requiring fresh reconnection rather than claimed as silently
  recoverable.

### Quality and performance

- Current source and exact candidate packages pass the relevant Rust,
  documentation, installer, package, and declared Linux live gates.
- Every bounded operation has a deadline or explicit cancellation and produces
  a truthful user-visible result.
- The frozen performance/stability thresholds from Phase 1.0B pass, with
  application/topology-specific exceptions documented rather than generalized.
- No P0 or P1 remains open. P2 items are either fixed or explicitly accepted
  as safe, non-blocking limitations.

## 7. Recommended next authorization

The route has now been consolidated to three bounded phases. Phase 1.0A,
1.0B and 1.0C are validated, and internal RC preparation is qualified. The
currently authorized scope is final `1.0.0` source/package qualification and
publication only after every release gate passes.

Do not authorize broad feature development before that decision.
