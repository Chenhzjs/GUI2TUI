## 1. 产品目标与边界

### 1.1 修订后的目标：在 TUI 中完整使用 GUI 应用

用户最终目标是“GUI 应用能在 TUI 里面完美地使用”。组件提取和操作是实现手段，
验收单位应当是用户工作流。不能以“有接口列表、能投递 click、错误解释清楚”
就宣布产品目标达成。

在指定应用版本、环境和工作流范围内，目标具体化为：

1. 用户能理解当前内容、状态和可用操作，知道自己在哪里。
2. 无需原 GUI 的鼠标帮助，可以发现、定位、执行所需操作并输入参数。
3. 一次操作后可以继续下一步，处理弹窗、错误、保存及取消。
4. 终端缩放、窗口切换和应用动态变化不会让用户丢失工作位置或误操作。
5. 日常交互响应可接受，不需要频繁刷新、重新搜索或手工调整预算。
6. 所需功能不能因为 GUI2TUI 的角色白名单、呈现遗漏或未知 effect 被挡住。

这里的“完美”追求功能和使用体验的完整，不要求复刻 GUI 像素布局。
在当前 Accessibility-only 和密码保护约束下，不能保证所有任意应用的全部功能：
未公开语义的画布、仅支持指针手势的交互、密码输入等要明确标为范围缺口，
不能把降级措辞当作实现完成。如果核心工作流确实受这些边界阻断，提交具体证据
和需要改变的产品约束给用户判断；实施者不能擅自绕过约束，也不能静默缩小目标。

### 1.2 对上一版方案的评估

上一版的逐对象追踪、通用性和身份约束是合理的，但有五处不足：

- 诊断先行过重，容易再次把主要时间花在统计工具，而不是修用户遇到的阻塞。
- “有入口或原因”只能算诊断完成，不能算能力完成；可修复的缺口不能只登记。
- 将所有新接口操作留到后续，会导致真实任务已经阻塞却仍宣布本轮完成。
- 原 20 项多为独立动作，新容器隔离不能证明同一会话连续工作可用。
- 易用性、默认 spatial 布局、响应速度及终端恢复没有成为验收条件。

修订为：先选工作流并实际使用，沿失败路径做最小诊断，补齐实现和呈现，
再验证连续使用。P0 是定位工具，不是必须先建成的独立系统。

### 1.3 实现原则

GUI2TUI 的核心只有两件事：

1. 提取组件：读取应用公开的对象、内容、状态、关系及操作能力，组织成可导航的 TUI。
2. 操作组件：把用户明确选择的操作准确投递给原 GUI 对象。

操作后更新组件信息，使界面跟随原 GUI。不要再把自动探索、effect 推断、
强 verifier 或风险词分类建设成用户操作的必要前提。

能力公开且目标可明确定位，就应展示对应操作；尚未实现的操作应说明实现缺口，
不能解释成“不安全”。全文替换可以按 provider 的语义替换格式及嵌入对象。
保留目标身份、session/generation/ticket、接口、真实模态范围、密码保护、
后端接受结果和必要的权威读回。任意 action 不要求预知 effect；
文本读回约束不应推广成所有 action 的执行门禁。

不要承诺从 Accessibility 中提取应用未公开的对象。禁止 app/toolkit 特化、
DOM/CDP/UNO、坐标点击、OCR、视觉语义、直接修改应用文件等替代执行路径。
本方案不扩展任意原始按键序列、不引入新的外部效果授权系统。

## 3. 先区分四类问题

| 类型 | 判定证据 | 处理 |
|---|---|---|
| 应用没有公开 | 只读公共接口也没有目标/能力，且没有本轮读取错误 | 说明已观察范围；不伪造 |
| 提取丢失 | 同一稳定场景公共对象存在，GUI2TUI cache 缺失或字段丢失 | 修 backend/cache |
| 呈现丢失 | cache 有信息，但 Surface/Reader/命令/F3 均无法到达 | 修投影与导航 |
| 操作缺口 | 公共能力存在，但没有实现入口，或精确调用路径有误 | 补已有操作链或有界接口操作 |

超时、节点预算、未展开结构和未实现接口要分别记录。一次读取失败不等于接口不存在，
一次隐藏不等于永久不存在。不要给“整个应用提取完整率”编造分母。

## 4. P0：建立最小的逐对象对应检查

目的：回答“公开对象/能力在哪里丢了”，不是建设第二套 benchmark/runtime。

复用已有 inspect、SemanticCache、SceneBinding、CommandHierarchy、F3 构造逻辑；
优先扩展现有诊断输出，避免独立框架。必要时将 F3 条目构造提取为小型纯函数，
供真实 TUI 与诊断共同调用，避免测试复制一套能力判定。

每条诊断记录至少包括：

- generation 和 BackendLocator（跨快照匹配不能只用 RuntimeNodeId）。
- 原始 role/name/interfaces/states/action names 与字段读取状态。
- cache 中的语义 role/capabilities。
- 可达入口：Surface、Reader、命令面板、F3；同一对象允许多个入口。
- 未到达原因：折叠但可导航、当前 scope 外、尚未加载、读取失败、预算截断、
  对象过期、接口尚未实现、无效/歧义 action 等。
- 展示名称与原始名称分开，派生标签不反向变成执行标识。

对照方法：

1. 选择静止场景，使用测试侧只读 AT-SPI 读取，和产品当前快照按 locator 对照。
2. 若两次读取之间对象变化，归为不稳定样本并重取；不直接算漏提取。
3. provider、cache、TUI 三层分别统计，区分原始对象数与可操作对象数。
4. 只有场景读取完整且范围一致时才报告覆盖比例；其他情况列出具体差异。
5. 检查“可达”而非“所有对象同时显示”。折叠到能打开的入口不算遗漏。

首轮对照只用已有公共接口 fixture，以及第 9 节选定工作流实际遇到的静止场景。
诊断验收：每个范围内公开对象/支持操作均有入口或具体原因；得到实际遗漏清单。
这不是产品验收。公开能力因 GUI2TUI 未实现而缺失时，仍是未解决问题。
不要仅因可记录状态增多就宣布功能提升。

## 5. P1：修组件提取、能力发现和动态更新

### 5.1 Cache 与 walk 的字段一致性

主要文件：src/backend/atspi.rs、src/backend/bootstrap.rs、src/semantic/cache.rs。

本轮代码阅读发现的待验证入口：

- role_needs_name 仍按角色决定缺失名称的补读。验证罕见角色且公开 Action 的
  对象是否因此漏名称；若复现，按字段缺失和公开能力安排补读，不按品牌判断。
- read_public_actions 对数量超过 256 返回 invalid public action count。
  区分非法计数与合法但超过预算；预算耗尽不应表现为“没有动作”。
- 动作名称、说明、快捷键的读取共处一次有界读取流程。验证可选说明超时是否
  导致已获得的名称全部丢失；必需执行名优先，可选元数据失败不清空能力。
- debug.interfaces 被多行资格判断使用。验证它在普通非 verbose 路径同样可靠；
  若不是，应复用已有语义接口字段，不能让 debug 开关决定能否操作。

这些是有依据的审查入口，不是已经证实的所有应用缺陷。逐项复现后最小修复。

验收：同一稳定 fixture 的 Cache/walk 给出一致的关键接口和动作名称；
局部可选字段失败不抹去其他已知能力；预算截断可辨识。
保留精确 action 名与当前索引的映射，不因分页/跳过失败项而重编号后调用错误对象。

### 5.2 多行编辑能力不依赖文档呈现分类

当前 qualify_complex_text_capabilities 只从 visible_models、Complete model root
寻找目标。即便后端已支持某个 EditableText，多行对象如果没有成为模型 root，
也可能没有入口。先构造普通容器中的完整多行文本控件验证此假设。

若复现：

- 从当前 scope 中的公开 Text + EditableText 对象发现文本操作资格。
- 文档模型负责组织内容；不作为“是否存在文本操作”的唯一来源。
- 保留完整文本读取、密码屏蔽、写前冲突与写后精确读回。
- 优先复用现有外部编辑会话，通过明确入口选择准确文本对象，避免必须先伪装成文档。
- 不因文档整体 Partial 就拒绝一个独立且可完整读取的文本对象；
  也不把局部对象替换宣传成整个文档替换。

验收：非文档模型根的公开多行 EditableText 能通过真实 TUI 编辑；
同一父容器有两个文本对象时，选择 A 不修改 B。

### 5.3 动态和虚拟化对象

复用现有事件、refresh、realization、content/virtual_collection 路径。
用户展开、切页或执行公开滚动操作后，按新鲜公共结构更新对应对象和入口。
未实现/未公开的滚动保持明确边界，不使用盲按 Down 或坐标输入补足。

先做一个展开后增加子项、折叠/删除后移除子项的场景。
验收：新对象进入导航，旧 F3 条目不再发往失效对象，焦点可恢复或清楚说明目标消失。
再按真实缺陷决定局部刷新优化；不先重写整个事件系统。
保留预算并给出可操作的刷新/提高预算提示，读取错误不能伪装成完整树。

## 6. P2：操作链与界面入口完善

### 6.1 复用公共操作执行约束

检查 F3、Enter、命令面板在身份和调用语义上是否一致。
重点文件：src/tui/app.rs、palette.rs、action.rs、operation.rs、transition.rs、
src/backend/atspi.rs、src/runtime/。

F3 不应仅为复用代码就把每种命名 action 解释成具备 Activate 的效果。
可以共享投递生命周期，但通用命名 action 只报告真实接受/拒绝/超时和刷新结果。

核查各路径：当前 session/generation/scope → 精确 locator → 当前接口/命名动作
→ ticket → 后端投递 → 结果与界面刷新。局部缺口优先修共享函数；
没有重复导致的真实问题时，不开展大规模重构。

### 6.2 现有能力完整可达

优先处理 P0 找出的“已实现但入口缺失”，而非先添加更多接口：

- 同一对象同时有 Action、Value、EditableText 时，不让默认主操作遮蔽其余能力。
- Selection 增删成员重新定位子对象；特别核实 deselect 接口索引语义与 provider
  的当前 child / selected-child 顺序，不能把两个索引空间混用。
- Value 读回实际值，达到边界、归一化、未改变都如实表达。
- action 名称歧义必须让用户看到原因，不能静默任选第一个。
- 没有默认 Enter 映射的对象，不能笼统写成“只读”，而同时把公开操作藏在 F3。

F3 已支持的命名 Action、多选增删、Value 增减不重复实现。
验收：实际选中哪个对象/操作，就调用该对象/操作；不同入口不改变能力含义。

### 6.3 尚未实现的接口操作：列出后再分批实施

对照表应区分：
“接口公开某方法”“本对象可尝试调用”“产品已实现入口”“实际已验证”。
例如 Value 直接设值、Text 光标/选区、EditableText 插入/删除、Selection
全选/清空，都需要调查当前是否已实现及公共方法语义，不能宣称此阶段全部支持。

后续优先级以实际任务缺口决定。每次只补一个有真实用例的参数化操作，经过同一
正常 authority 链，验证参数、偏移单位、范围、当前对象身份，并有明确 TUI 输入入口。
参数合法性是接口要求，不是额外风险审查。
不要为了“完整”开发一个包含所有 AT-SPI 方法的通用 RPC 控制台。

选定工作流若被上述公开接口缺口阻断，6.3 的对应操作属于本轮实施范围，
应直接补齐并验证，不能只交清单。无需为每个正常实现选择另行请求许可。
与选定工作流无关的接口扩展仍列入后续，不自动开展全接口实现。

不把所有组件交互都压成 click：例如选择文本范围、设定精确数值需要参数入口；
一次全文替换不能被当作已经支持选区编辑。按公开能力决定具体交互。

## 7. P3：让提取结果更容易使用

只改 presentation，不改变 backend 身份、角色或能力：

- 使用公开 label 关系、名称、说明、祖先上下文改善显示；
  缺失时显示角色和位置上下文，不能猜实际功能。
- 去掉纯装饰的重复文字时，保留所有可操作对象和可恢复来源映射。
- F3 优先帮助定位当前对象，同时保留整个当前 scope 的可搜索列表；
  搜索、分组、翻页不得静默截断。
- 同名对象显示有意义的容器路径/角色；快照 ID 作为补充消歧。
- 明确“当前场景部分加载”，提供刷新或预算提示，不把大量技术字段塞进日常界面。
- 保留现有 Enter、冒号、F3 按键习惯；帮助文档解释各自用途。

验收：命名操作、同名消歧、多选、编辑在 flat/spatial 均可经实际终端导航到达；
测试折叠和窄终端情况下的可达性，不以截图相似为目标。
不要求所有信息同时常驻主界面。

## 8. Mousepad 两个剩余任务的独立排查

先不修改产品，不修改原断言；保留 18/20 基线：

1. 从原始结果定位实际对象、父菜单和精确动作名，确认日志对应请求的目标。
2. 只读检查 menu item 的子对象、关系、属性和状态，看看 CHECKED 是否在另一个

3. 通过 GUI2TUI 再打开菜单，取新对象而非缓存旧 proxy 的状态；观察是否存在延迟

4. 必要时录屏由人核对菜单勾选、行号、长文本换行。截图/视频仅作人工测试证据，

5. 若 provider 不公开结果，报告“投递接受、公共效果不可确认”，保留原任务未通过。
   若人工证据确认效果，可以另列人工确认，不能回写为原自动断言通过。
6. 若自动断言找错状态对象，提供公共关系证据，新增修订版断言并保存前后结果；
   不使用 app-specific production rule。
7. 若是投递链 bug，修通用后端/菜单生命周期并复跑两个任务。

此项的完成条件是确定根因或用具体证据标明无法判断的边界，不强求 20/20。

## 9. 用连续工作流驱动实施与验收

### 9.1 首批工作流与真实使用要求

保留原 20 项作为历史回归，另复用现有 PTY runner 增加以下少量连续流程。
每个流程从启动到结束使用同一个应用会话，不能每一步 reset 来绕过动态问题。
应用名称、目标文字和操作步骤只允许出现在测试中。

| 工作流 | 连续任务与验收点 |
|---|---|
| 文本编辑 | 新建 → 输入含中文和多行的文字 → 查找 → 通过 GUI 保存对话框保存到临时目录 → 再编辑 → 取消一次关闭 → 再关闭并丢弃 → 通过 GUI 重开 → 确认保存内容 |
| 浏览器 | 输入本地测试网址 → 跳转 → 通过页面公开控件填写表单并提交 → 读取新内容 → 新建/切换/关闭标签 → 回到原页面继续操作 |
| 文档阅读 | 通过 GUI 打开多页测试 PDF → 查找文字 → 跳到下一页 → 调整缩放 → 切换侧栏 → 继续阅读当前内容 |
| 通用接口补测 | 两个同名对象消歧 → 指定文本对象编辑 → 多选增删 → 数值调整 → 动态增加/移除控件后继续调用当前对象 |

实现顺序先文本编辑、浏览器，再文档阅读；fixture 仅针对实际缺口补证据，
不能用 fixture 成功替代真实应用成功。优先在 Mousepad 验收文本流程，

### 9.3 可用性和响应标准

- F3 是全部公开操作的可发现入口；常用工作流不应要求用户记 locator 或快照 ID。
  主场景和上下文操作优先支持当前目标，仍保留全 scope 搜索。
- 已缓存的导航/搜索应立即反馈；后台读取应显示进度，并允许取消。
  不允许一个慢对象长期阻塞整个终端，也不能悄悄丢掉其他可用操作。
- 记录首屏时间、按键到终端反馈、投递耗时、刷新耗时。先测基线，
  将 p95 本地导航反馈低于 100 ms 作为工程目标；真实应用等待单独统计，
  amd64 模拟环境结果必须标明，不能宣传为所有机器的性能。
- 长操作至少在 1 秒内显示进行中状态；具体超时继续使用有界后端配置。
  不把超时缩短当性能修复，也不因刷新失败自动重放已接受的有副作用动作。
- 主流程在默认 spatial 的常见终端尺寸（如 120×40）完成；
  窄终端（如 80×24）重点验证目标/操作可达、提示未丢失和恢复。
  flat 保留原 20 项回归；不要求所有任务做所有尺寸的笛卡尔积。
- 弹窗关闭、列表刷新、标签切换后保留合理上下文，防止每步都重新寻找目标。
- 外部编辑器返回后 TUI 正常接管，退出恢复终端；场景中没有可操作对象时给出原因。

这些是待测验收目标，不是当前已有性能结论。若不满足，记录具体耗时与瓶颈，
选择局部刷新、延迟读取或分页等最小修复，不直接移除所有预算。

### 9.4 结果判定与停止条件

产品验收：用户工作流通过真实 GUI2TUI 完成、无需原 GUI 补操作。
测试可以检查任务结果，人工也可确认；产品本身不新增 effect 推理门禁。

- 调用被接受：只证明交付链路；不能代替保存、跳转、选择等任务结果。
- 任务通过：独立只读断言或明确记录的人工观察证实预期结果，注明证据类型。
- 因 GUI2TUI 丢失公开能力而失败：可修复阻塞，持续修复，不能只登记结束。
- provider 未公开/环境失败：给出公共接口和复现证据，作为有边界的阻塞报告；
  保留未完成，不宣称功能等价达成。
- 使用不便但任务可完成：记录实际导航步骤、重复搜索/刷新情况并优化关键路径。

阶段 D 结束时必须逐条交代所选工作流，而不是仅展示整体通过率。
选定工作流全部通过，或剩余阻塞已证实超出现有公共接口/项目约束且无法继续处理，
才可结束该阶段并如实交接。后者是“部分完成并受阻”，不是“完美可用”。
不自动启动发布、任意接口大全或与选定工作流无关的新研究。
后续按用户实际应用和工作流扩展范围，持续维护功能对应和任务可用性。
